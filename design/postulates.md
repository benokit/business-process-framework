# Framework postulates

- **P1 — Everything is data.** This is the fundamental postulate. It has no representation as an element; it defines what an element is. An element has the properties `id`, `kind` and `data`.
- **P2 — Fundamental concepts.** Data is the fundamental concept (P1). The most primitive *element* is the abstraction: the kind, whose kind is `kind`. (Earlier set: data, schema, execution.)
  - *Open:* how behaviour is associated with an element.
- **P3 — Effects vs. pure code.** Side effects are decoupled from pure code.
  - A pipeline **node** represents a side effect.
  - **Data flow** at node boundaries is controlled by **pure functions** (mappings).
  - The **JSON representation** is the semantic boundary between the two.
- **P4 — `low` node.** `low` calls a host-language (JS) implementation of a side effect. It can't mutate context keys.
- **P5 — Complex pure functions.** Pure logic too complex for the expression language may be written in the host language. The implementer is responsible for its purity.
- **P6 — Data composition.** The framework's data composition primitives are defined by postulate: `/data`, `/ref`, `/merge`, and the operations of the algebra (P21).
  - We certainly need a mechanism to author complex queries separately. Introducing /file as a data composition tool is a good idea, but an url or uri should be more robust (no relative paths).
- **P7 — Schemas.** Schema data has the shape of a compact schema. Validation is done by AJV, which also resolves `$ref`s; the framework doesn't. Schemas are registered with AJV in the load phase; AJV compiles each schema lazily, at most once, when a validation is first requested.
- **P8 — Operations.** Operations are a primitive property of the kind. They are invoked through an instance.
- **P9 — Instance data.** An instance's data is defined by the shape of its kind, and nothing more. No keys are reserved in it.
- **P10 — No service kind.** There is no `service` kind. An element with operations is an instance of a kind that defines them.
- **P11 — Open slots.** A package may declare new slots on a kind it doesn't own.
- **P12 — Slots and middleware.** A slot fill can be any data. A generic middleware node accepts a sequence of executables and runs them in order; each receives `next` (the continuation) and is responsible for firing it.
- **P13 — Context.** A kind specifies the context it manages (a schema): context keys and their value schemas. No element demands the existence of context it doesn't manage. Two elements can't manage the same context unless they are from the same hierarchy tree. There is no extra benefit in requiring the explicit declaration of context keys an element could access: there is no restriction in which key is read (handles included). In messaging, the publisher decides which part of the context it propagates in the message; the consumer kind manages its own key.
- **P14 — Minimal core, durability outside.** The core takes care of really fundamental concepts that are necessary to build arbitrary systems. It doesn't provide durable execution; the framework provides all means to build it, if needed, in terms of messaging and pipelines.
- **P15 — Program against interfaces.** The framework provides a mechanism to reference kinds rather than instances (specific implementations): a mechanism to program against interfaces.
- **P16 — Explicit API.** No method is exposed automatically via the API. Adding an endpoint is cheap; whatever needs to be exposed on the API is exposed explicitly.
- **P17 — Entity traits.** Stateful entities are not fundamental; they are derived from a more fundamental entity model. An entity is extensible by other traits without changing the db model. For example, a versionable trait: the data has a special protected property with all versions associated with validity intervals. Such an approach gives the possibility of unlimited additional traits. Collision of properties is avoided by putting the entity data in `data/body`, considering body as a fundamental entity trait.
- **P18 — Open contracts across boundaries.** There does not have to be a rigid standardised way to propagate information across boundaries of execution (message, db write/read) upon which a system can rebuild a desired context. The contract between the execution systems should be open and up to the specific use case.
- **P19 — Security at the boundary.** The security layer lives on the surface boundary of the application, at the points where users interact with the system. Each HTTP endpoint is explicitly associated with a logical operation that has a checkable representation (plain dimensions): the endpoint prescribes a rule that maps a request to it. Operation representations are associated with roles. A security middleware turns a request into its operation representation and resolves the permission against the user's roles: permitted when at least one of the user's roles is associated with the operation.
- **P20 — Actors between modules and roles.** A module doesn't know the roles of the application that uses it. It introduces **actors**: permission aggregates that represent a business participant meaningful within the module (an underwriter, a user administrator), each granting the operations that participant performs. Roles belong to the application's global scope: they assign actors, may grant the application's own permissions directly and may include other roles (an aggregate); users hold roles. A module grants permissions and assigns work (process tasks) to its actors, never to roles.
- **P21 — Data composition algebra.** `/data` composes data by a type-agnostic algebra: `merge` (default; objects recurse, everything else replaces), `replace`, `unset`, `append`; associative, with absent as identity. A schema is never combined by the algebra: it has its own primitives (all-of, any-of, one-of, ref). Inheritance composes no data with markers. Elaboration: [data-composition.md](data-composition.md).
- **P22 — Kind values and settings.** A kind has no `defaults`. Values a kind supplies and no child or instance changes are `fixed` (united along the chain; a different value for the same path is a conflict). What a deployment tunes are **settings**: a schema and defaults declared by the kind, overridden by subkinds and instances (defaults compose by plain override), by `app-config` and by environment variables; source ranks above specificity. Settings are modelled to be managed entirely by environment variables (primitive leaves, identifier names, an explicit mode enum for variants). Settings are namespaced by element id and never in `_ctx`. Elaboration: [kind-settings.md](kind-settings.md).
