# Critique

Open improvement proposals and open questions about the framework, measured against the [project goals](project-goals.md) (G*) and [postulates](postulates.md) (P*). IDs are stable so they can be referenced; resolved items are removed (the last version with them is commit `c78a374`).

Status: **open** (proposed, not yet decided) · **agreed** (decided, not yet built) · **in progress**.

---

## Improvement proposals

| ID | Proposal | Status |
|---|---|---|
| F37 | **More interpreters.** The [test interpreter](../implementation/core/README.md#interpreters) replaces operations by stubs and refuses `low` nodes of other effect classes. Built: the dry run as the `skip` of `traced` (a skipped `low` node answers `null`, so downstream nodes may fail: the trace shows where). Proposal: a dry run (operations with `write` or `irreversible` effects are skipped or answered, `read` runs) and an audit interpreter (records every effect reached). Open: what a skipped operation returns in a dry run, where its output feeds the next node. | open |
| F38 | **Index maintenance as a durable ETL.** The [entity-search](../implementation/entity/entity-search/README.md) consumer keeps an index current, and `entity-search.reindex` fills it again. Two operations are needed: *reindex* (the structure of the index, its `mapping` or `settings`, has changed, so every document is derived again against the new structure) and *recreate* (the index is cleared and every document inserted again). Today's `reindex` is in fact a recreate, and a naive one: one pass, one insert and one wait per record, only the first 200 records, nothing resumable. A proper implementation is a durable ETL (extract the records, transform with the mapping, load into the index): it runs in pages, records its progress and resumes after a crash, and doesn't lose changes the consumer makes while it runs (for example by building a new index and swapping it in). Open: whether a durable ETL is a kind outside the core, built like durable processes (Q3). | open |
| F40 | **Data shapes through pipelines.** Done: `validate()` infers every expression from the type of its scope ([data flow](../implementation/core/README.md#data-flow)): misspelled scope, output and context keys, keys missing from objects built in code, mismatched operands and pure function arguments are found before run time; slot fills get the `input` their slot declares; template nodes and methods have output types; a computed `invoke` target stands for the elements its type names (references are typed by the ids of a kind's instances), so outbox delivery and search are no longer counted as every effect class. Declared objects of contracts and shapes are closed for inference, so paths into contract data are checked too; maps and `"*"` stay open, and run time is unchanged. Remaining: (1) `entity-event.entityType` stays `string`, since a message may name entity types another application doesn't have (P18), so `entity-search-service.index` still counts every effect class (operation inputs that name an entity type are `@ref/entity-type`); (2) what a computed `execute` runs, and the outputs of `execute`, `low` and `middleware`, stay unknown; (3) what an `invoke` passes isn't checked against the input contract of its target: `{ "inputMap": { "entityType": "partty", … }, "invoke": "entity-states", "operation": "transition" }` passes `validate()`. | in progress |
| F9 | **Pipeline granularity.** Orchestration-level pipelines (named business steps, waits between pipelines, declared extension points) are worth keeping as data: they enable durability, diagrams, analysis and step extension. Fine-grained computation is not: it belongs in mappings and pure functions. Steps others may extend must be declared (slots), because step names become public API (fragile base class). Precedents: Step Functions and BPMN (data), Temporal (code plus replay). | open |
| F11 | **Checked pure functions (P5).** Effects are inferred, bounded and stubbable. `validate()` checks the arguments of every `$func/<id>` call against its `signature` ([data flow](../implementation/core/README.md#data-flow)); nothing checks them at run time, nor a function's result, nor that a mapping-based function returns what its signature declares. Proposal: check arguments and results against the signature at run time; check the inferred result of a mapping-based function against its `output` in `validate()`; run declared `examples` in `validate()`; freeze inputs; a lint configuration for pure modules; a determinism test; optional SES sandbox. Since purity is the implementer's responsibility, the runtime may then cache, replay, version and run pure functions at load time, but never effects. | open |
| F12 | **Place each kind of logic where it fits:** glue in mappings; tabular and rule logic in declarative kinds (decision tables, lookups); algorithmic logic in JS pure functions. Build large logic from small named pure functions. First candidate: a decision table kind for rating or eligibility. | open |
| F43 | **Delivery.** The framework is delivered as npm packages, one per module, in a private registry (GitHub Packages), all under one version (a framework version is a set of packages that work together). Its public API is the element ids and contracts (kinds, operation contracts, integrations, schemas, slots): renaming or removing one is a breaking change. An application is an npm project: its `dependencies` are the modules it is made of, so replacing a module is replacing a dependency (G9), and `validate()` lists the integrations the replacement leaves unimplemented. Beside them: its own elements, JS modules and files referenced with `/uri`. The server loads the application's declared modules (with what they depend on), never whatever is installed; today it scans the monorepo's `node_modules` and so can't run an application outside it. A scaffold (`npm create business-framework`) writes a new application: dependencies for the chosen adapters, local infrastructure for them (compose), a Dockerfile and the agent instructions (G8). The application builds its own container image; configuration comes from `BPF__` variables, so one image runs in every environment. | agreed |
| Q3 | **Durable processes outside the core (P14).** Waits happen only between pipelines, never inside one, so scoped context and `next` never cross a wait and the core needs no execution log or replay. A durable process is a kind built from entity states, message consumers and delayed messages. Already given: a state change and its messages commit atomically (outbox); a stable `messageId` lets consumers be idempotent. Missing: delayed or scheduled delivery (the only way to express a timer), and routing a message to its process instance (a correlation key chosen by the publisher). Open: whether delayed delivery is a messaging capability or a scheduler kind. Versioning running processes is the process kind's concern (pin the definition per instance). | agreed |
| F21 | **Execution tracing** as an interpreter, not runtime code. Built: `traced(run, { skip })` records the spans of a run (operations, slot fills, node templates, steps, `low` nodes with their effects) by decorating the place frames are made, so untraced code is unchanged; `bpf trace <element> <operation>` prints them. Open: diagrams (a Mermaid sequence from the spans), spans for `forEach` iterations, assertions on spans in tests, an optional recording of values for tests. | in progress |
| F52 | **Failure diagnostics.** An error says why it failed (`code`, `message`, `data`) but only an `invoke` contract check says where; a failure deeper in a pipeline arrives without the route, and a `low` module throws a raw JS error with a stack inside the interpreter. Proposal: an error that unwinds collects **frames**, one per level, added where it passes (`runSequence`: the node index and its keyword or `inputMap`; `invoke`: `element.operation`; the id of the slot fill or node template whose code runs) and kept in `data.frames`; nothing is recorded on success, so there is no run state, `_ctx` stays clean and a caught error leaves nothing behind. A foreign error from `low` becomes a `CoreError` (`low-failed`, `data.module`, `data.export`, `cause`). One formatter renders `code: message` and the frames (`orders.create > step 3 (execute) > pricing.quote > step 1 (inputMap)`) for logs, tests and the CLI. HTTP responses carry the code and the message, never frames or node sources; values are never revealed. Independent of F21, which traces runs that succeed. Built: frames, `low-failed`, `describeError` (used by `bpf`), the HTTP server and the NATS consumer log a failure with its correlation (a message dropped after its retries is no longer silent), HTTP errors carry the correlation. | done |
| F22 | **Entity traits (P17).** A record's `data` is a map of traits: `body`, the business data, and every other key (`state`, `versions`, …). `body` is the trait `body` like the others (owned key, written through its command `entity-bodies.put`, revisioned, seen by slots and events alike), declared by `fixed.traits.body` of `entity-type`; its schema is the configuration under `traits.body` in the entity type's data. All traits share one JSONB column and the revision history, so a new trait needs no migration. Rules: one owner per key; a trait's key is written only through the trait (`entity-type.writeTrait`), which carries the other keys over. A trait is an `entity-trait` element whose id is its key, with a configuration schema. `entity-type` declares one slot, `traits` (many `{ trait, configuration }`): an entity type uses a trait through a fill on itself, its class or `entity-type`; the effective use of a key is the deep union of the `fixed.traits` of the kind chain, the `traits` of the entity type's data and the fills, a different value at one path being a conflict, and keys introduced only by fills are closed to the data ([body-trait](body-trait.md)); `validate()` checks the trait, its configuration, undeclared and repeated uses through the kind's `validate` hook. A trait initializes its value on `create`; its commands are operations of its own service, exposed by its own endpoints (P16). Changes and events name the trait and the command. The case that raised whether one trait may derive another's key (a timeline keeping `body` as the version valid now) is closed by the versioned body: the body itself is versioned ([versioned-body](versioned-body.md)). | in progress |
| F46 | **Pure side, against the goals.** The pure side serves data flow between nodes (P3), conditions (guards, `validate` hooks), derived data (slot mappings) and business rules (G1, G10); P5 leaves algorithmic logic to JS pure functions. P3 is met by construction. The language's semantics are settled (`lambdajson-js` 3: strict operands, deep equality, functions with named parameters, typed primitives). What remains in the framework, by owner: **framework packages** (G1, built from primitives by G7, not added to the language): money as decimals with explicit rounding, and pure date arithmetic (add days, compare, period length), as `pure-function` elements. **Core**: checked signatures and `examples` (F11), rule kinds (F12). | open |
| F54 | **An abstract "now" for the application, not for the framework ([P23](postulates.md)).** A versioned body reads the last version by default, which is not the version in force today once a later-dated one exists. The framework must not know the date, so the date has to come from outside. Proposal: a reference date as a context key (`validAt`) managed by one kind, bound by the layer that controls the request (the security layer, or an application setting such as "today", "last version" or a fixed date for a replay), and read by `read` as the default of `at`; without it nothing changes. Needed before more features build on versions: guards, rules, ownership and search all see the last version. Questions: who binds it and from what (a setting, a header, a claim), whether it also feeds search and relations, and whether it carries a time zone. | open |
| F58 | **A typed change and typed references to operations.** `entity-change` is an `operation` enum with optional `commands`, `before`, `after` and `entityOperation`, so a guard can't rely on which fields exist; `entityOperation` is a string that operations by state, state permissions and guards match by name, and `refs` can't trace it. Proposal: the change a one-of by `operation`; `entityOperation` a reference to an operation of the entity type, checked by `validate()` and found by `refs`. | open |
| F59 | **The store contract.** `entity-store` declares its operations with `@any` input and output; the contracts live on the queries, so a second store has nothing typed to implement (P15). `create-entity` requires `data.body`, while the design says `entity-record.data` is any object and an entity without business data is possible: the two disagree. `list` has a limit and no contract for paging. Proposal: typed operations on `entity-store`; the `body` requirement leaves the store (`entity-type` no longer fixes the trait `body`, R6.15). | open |
| F60 | **What a trait command is.** A trait operation returns `{ command, value }`, but the store writes the key's whole value; the command survives in changes and events, not in storage, and a versioned body rewrites its timeline at every amendment. Decide: commands are part of the model (stored, an audit trail for free) or metadata of the change (said so, in the owner). | open |
| F61 | **`entity-states` carries four concerns:** the state machine, the permission dimension, operations by state and move restriction. The permission dimension links to [state-permissions](state-permissions.md) by a naming default (`status`), operations by state to the entity operations by name (F58). Proposal: the state machine stays; permission state and operations by state move beside what reads them, once F58 gives them a reference to hold. | open |
| F62 | **Smaller observations on the entity model.** (1) Composition is final by design (P22): no override of a default, arrays equal, no append to an injected list; the first real case that needs one decides whether the algebra gets a rule ([body-trait](body-trait.md) §6). (2) `trait-initializer` and `trait-operator` exist only to invoke a trait by id: a sign that a computed `invoke` target lacks something, not an entity matter. (3) To verify: `traitsOf` is computed at every call, so every write recomputes the union of the traits unless it is cached; and whether the revision history stores full snapshots, which a timeline makes large. | open |
| F63 | **Stored derived facts and time (P23).** Ownership is derived at write time from the last version of a versioned body and stored once ([row-access](row-access.md)). A future-dated amendment that moves a contract to another region changes the access today, so access follows the date of the write and not the date the change takes effect; with a reference date (F54) reads become time-dependent while the stored fact stays fixed, so the search filter and the guards can disagree. The same holds for every fact a trait derives and stores. Options: derive per version (the fact becomes a timeline), or declare that a stored fact always describes the last version and that access control is not time-dependent. Open: which, and what a rule reading the body sees. | open |
| F64 | **The storage format of a trait is not versioned.** The stored value of a trait depends on the trait and its configuration: a plain body and a timeline are different JSON, so turning `versioned` on, or putting another trait under a key (R6.15), leaves existing records in the old format and their reads fail. Ownership has a one-off backfill, but there is no general step "the storage format of this trait changed, migrate it". Proposal: an operation `migrate` of the trait (the old value and configuration to the new value), run for every record of an entity type as a migration like the ownership backfill, and a `validate()` check or a documented rule that a change of the trait or of its storage-relevant configuration comes with one. | open |
| F65 | **Amendments with a shape of their own.** Today `propose` takes a JSON Patch from the caller and the amendment body is that patch merged into the amendment type's data (`amendedType`, `amendedKey`, `effectiveFrom`, `patch`). The amendment holds no document: it can't be validated before `apply`, a reviewer sees a patch, and it applies to whatever the last version is then (the base is not recorded). Proposal: the amendment is an entity with a **shape of its own**, and the entity type that permits it says how the two meet, in the fill of its `amendmentTypes` slot, as pure mappings: (1) `open`: `{ entity, input }` (the viewed record of the amended entity and the input of the proposal) to the amendment's initial body; (2) `apply`: `{ body, amendment }` (the last version and the amendment's body) to `{ validFrom, body }`, the new version. (3) The input of `propose` is arbitrary: `propose({ entityType, businessKey, amendmentType, input })`, where `input` is checked at run time against the `input` schema of that fill (a contract that depends on the instance, Q6). The amendment copying the last version (`open` returns the entity body, `apply` returns the amendment body) and the patch-based amendment (`apply` applies a patch with a pure function) are two fills, not two mechanisms. The facts the process owns (the amended type and key, the revision the amendment was opened at, the date) leave the body for a trait `amendment-link`, so the shape is the application's alone; `apply` refuses when the entity is no longer at the recorded revision. The trait operation `amend` takes `{ validFrom, body }` (the backward patch is computed by the trait, as `appendVersion` does), and the patch is a detail of one mapping. `validate()` types the mappings against the body schemas of both sides, and the resulting version is checked against the body schema at run time. A preview of the new version before `apply` is the `apply` mapping run on the current amendment. Open: whether the fill value of `amendmentTypes` stays a bare reference when the mappings are the identity, and who may see the unapplied new version. | open |
| F66 | **Traits are an independent axis: exposing trait operations without a kind per trait.** `stateful-entity-type`, `owned-entity-type` and `versioned-entity-type` exist only to expose the operations of one trait (`transition`, `deriveOwnership`, `applyAmendment`), and an entity type extends one kind, so a composition of traits means choosing an order or redeclaring operations by hand (the demo does). Principle: each entity type composes its own traits; a composition with business value is provided as an abstract generative element (a class that fixes data), never as a wrapper of one trait. Since behaviour belongs to kinds and instances add no operations (P8, P9), exposure becomes data selecting from a generic mechanism: `entity-type` has `create`, `read`, `delete` and one operation `perform({ operation, businessKey, revision, input })`; the data `expose` maps entity-level operation names to trait operations (`{ "update": { "key": "body", "operation": "put" }, "transition": { "key": "state", "operation": "transition" } }`); `perform` looks the name up and runs it through `applyTraitOperations` with `entityOperation` set to the name, so guards, operations by state, state permissions and authorization keep their names. A trait marks which operations may be exposed (`ownership.derive` stays private). Operations that combine traits stay operations of domain kinds, with the `traitOperation(s)` nodes. HTTP stays explicit (P16): an endpoint names an exposed operation. The names of `expose` are what F58 references. Cost: the input of `perform` depends on the name called (Q6), so `validate()` must check the endpoints and the state models against `expose`. Open: whether `expose` is composed like the traits (union along the kind chain, conflicts), and whether a trait may declare a default name for its public operations. | open |
| F47 | **Evaluating pure code from the CLI.** `bpf eval <pure-function or element path> <input>` runs a mapping or pure function with a given input and prints the result, so authors and agents try a rule without booting infrastructure or writing a test; declared `examples` (F11) run the same way. | open |
| F48 | **Kind values and settings, what remains.** Built as designed in [kind-settings.md](kind-settings.md) (P22, R10). Open: the type of `$func/settings` isn't inferred, so `validate()` doesn't check paths into it; a warning for a setting no code reads; secret settings (relevant if `explain` ever shows effective values); checking the `fixed` values of a kind without instances against its shape; a data operation marker left in an element's `data` outside a `/merge` isn't reported. | in progress |
| F29 | **Read-only values beside a middleware chain.** A middleware method sees only what the previous one passes on. Entity interceptors receive `{ operation, input }`; the store write ignores a changed `operation`, but interceptors after the one that changed it see the changed value. Proposal, when a case needs it: the middleware node passes a read-only part beside the chain input. | open |

## Open questions

- Q4: Code generation at load time: should a kind's `load` hook be able to expand an instance into further elements or pipelines, and if so, how does an expansion embed load-time values into the LambdaJSON trees it generates, and is generated code validated against the kinds it targets?
- Q6: Contracts that depend on the instance: how an operation's input or output schema refers to `self` (the `traits.body` of `create` is checked against `self.data.traits.body.schema`), instead of each operation checking it in its implementation.
- Q17: File and folder conventions. Elements carry all meaning (`id`, `kind`, slot fills, `context`), so a path that also means something would be a second, hidden metadata channel that can disagree with the element. **Proposal:** the runtime ignores paths; conventions serve people and tools and are enforced by a lint check, not by semantics. Candidates: organize by feature, not element type; a kind is defined in a file named after it, or id prefixes match the package; a uniform package shape (`elements/*.eson` next to `src/*.js`), with `low` references resolving to modules of the package or its declared dependencies. **Open:** what folder conventions usually stand in for is a package boundary (exports, dependencies, which elements outsiders may invoke or fill slots on; today any element may do both). If wanted, declare it explicitly, in line with author-based binding rights, rather than infer it from folders.
- Q21: Validated solutions: `validate()` runs on demand, never on start. Should a start check that the element set it runs is the one validated (a fingerprint), or is that left to the deployment?
- Q22: Reusable methods with effects. Today a library is a service element whose operations are its methods: a namespace, a contract per method, replaceable through a subkind or binding. A library method gets what it needs through its input, never from the caller's `self` (shared behaviour on `self` belongs in a common base kind). Open: whether a free-standing counterpart of `pure-function` is worth adding (an element with a `signature`, run with its input and the bound context only); decide when the first library shows whether a service element is too heavy.
