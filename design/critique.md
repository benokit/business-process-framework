# Critique

Open improvement proposals and open questions about the framework, measured against the [project goals](project-goals.md) (G*) and [postulates](postulates.md) (P*). IDs are stable so they can be referenced; resolved items are removed (the last version with them is commit `011bc91`).

Status: **open** (proposed, not yet decided) · **agreed** (decided, not yet built) · **in progress**.

---

## Improvement proposals

| ID | Proposal | Status |
|---|---|---|
| F37 | **More interpreters.** The [test interpreter](../implementation/core/README.md#interpreters) replaces operations by stubs and refuses `low` nodes of other effect classes. Proposal: a dry run (operations with `write` or `irreversible` effects are skipped or answered, `read` runs) and an audit interpreter (records every effect reached). Open: what a skipped operation returns in a dry run, where its output feeds the next node. | open |
| F38 | **Index maintenance as a durable ETL.** The [entity-search](../implementation/framework/entity-search/README.md) consumer keeps an index current, and `entity-search.reindex` fills it again. Two operations are needed: *reindex* (the structure of the index, its `mapping` or `settings`, has changed, so every document is derived again against the new structure) and *recreate* (the index is cleared and every document inserted again). Today's `reindex` is in fact a recreate, and a naive one: one pass, one insert and one wait per record, only the first 200 records, nothing resumable. A proper implementation is a durable ETL (extract the records, transform with the mapping, load into the index): it runs in pages, records its progress and resumes after a crash, and doesn't lose changes the consumer makes while it runs (for example by building a new index and swapping it in). Open: whether a durable ETL is a kind outside the core, built like durable processes (Q3). | open |
| F40 | **Data shapes through pipelines.** Done: `validate()` infers every expression from the type of its scope ([data flow](../implementation/core/README.md#data-flow)): misspelled scope, output and context keys, keys missing from objects built in code, mismatched operands and pure function arguments are found before run time; slot fills get the `input` their slot declares; template nodes and methods have output types; a computed `invoke` target stands for the elements its type names (references are typed by the ids of a kind's instances), so outbox delivery and search are no longer counted as every effect class. Declared objects of contracts and shapes are closed for inference, so paths into contract data are checked too; maps and `"*"` stay open, and run time is unchanged. Remaining: (1) `entity-event.entityType` stays `string`, since a message may name entity types another application doesn't have (P18), so `entity-search-service.index` still counts every effect class (operation inputs that name an entity type are `@ref/entity-type`); (2) what a computed `execute` runs, and the outputs of `execute`, `low` and `middleware`, stay unknown; (3) what an `invoke` passes isn't checked against the input contract of its target: `{ "inputMap": { "entityType": "partty", … }, "invoke": "entity-states", "operation": "transition" }` passes `validate()`. | in progress |
| F9 | **Pipeline granularity.** Orchestration-level pipelines (named business steps, waits between pipelines, declared extension points) are worth keeping as data: they enable durability, diagrams, analysis and step extension. Fine-grained computation is not: it belongs in mappings and pure functions. Steps others may extend must be declared (slots), because step names become public API (fragile base class). Precedents: Step Functions and BPMN (data), Temporal (code plus replay). | open |
| F11 | **Checked pure functions (P5).** Effects are inferred, bounded and stubbable. `validate()` checks the arguments of every `$func/<id>` call against its `signature` ([data flow](../implementation/core/README.md#data-flow)); nothing checks them at run time, nor a function's result, nor that a mapping-based function returns what its signature declares. Proposal: check arguments and results against the signature at run time; check the inferred result of a mapping-based function against its `output` in `validate()`; run declared `examples` in `validate()`; freeze inputs; a lint configuration for pure modules; a determinism test; optional SES sandbox. Since purity is the implementer's responsibility, the runtime may then cache, replay, version and run pure functions at load time, but never effects. | open |
| F12 | **Place each kind of logic where it fits:** glue in mappings; tabular and rule logic in declarative kinds (decision tables, lookups); algorithmic logic in JS pure functions. Build large logic from small named pure functions. First candidate: a decision table kind for rating or eligibility. | open |
| F43 | **Delivery.** The framework is delivered as npm packages, one per module, in a private registry (GitHub Packages), all under one version (a framework version is a set of packages that work together). Its public API is the element ids and contracts (kinds, operation contracts, integrations, schemas, slots): renaming or removing one is a breaking change. An application is an npm project: its `dependencies` are the modules it is made of, so replacing a module is replacing a dependency (G9), and `validate()` lists the integrations the replacement leaves unimplemented. Beside them: its own elements, JS modules and files referenced with `/uri`. The server loads the application's declared modules (with what they depend on), never whatever is installed; today it scans the monorepo's `node_modules` and so can't run an application outside it. A scaffold (`npm create business-framework`) writes a new application: dependencies for the chosen adapters, local infrastructure for them (compose), a Dockerfile and the agent instructions (G8). The application builds its own container image; configuration comes from `BPF__` variables, so one image runs in every environment. | agreed |
| F44 | **Migrations as a separate step.** Adapters create their tables at start (`models` fills with `CREATE TABLE IF NOT EXISTS`): a changed table is never altered, and replicas starting together race. Migrations run as a separate step before a rollout (a `bpf` command run as a deployment job), and a start only checks that the database is at the version it expects. Open: how a migration is declared (ordered, versioned steps per adapter package in the `models` slot, or a kind of its own), where the applied versions are recorded, and how an application adds migrations of its own. | agreed |
| Q3 | **Durable processes outside the core (P14).** Waits happen only between pipelines, never inside one, so scoped context and `next` never cross a wait and the core needs no execution log or replay. A durable process is a kind built from entity states, message consumers and delayed messages. Already given: a state change and its messages commit atomically (outbox); a stable `messageId` lets consumers be idempotent. Missing: delayed or scheduled delivery (the only way to express a timer), and routing a message to its process instance (a correlation key chosen by the publisher). Open: whether delayed delivery is a messaging capability or a scheduler kind. Versioning running processes is the process kind's concern (pin the definition per instance). | agreed |
| F20 | **Security layer (P19, P20).** `authenticated` binds the principal when an OAuth token is valid, and nothing requires one: every endpoint serves anyone. **Operations.** An operation is a point in a space of plain dimensions, by default `{ area, resource, action }` (`{ "area": "entities", "resource": "party", "action": "update" }`), strings without structure. **Extensible dimensions:** the dimensions are fills of a slot `dimensions` of the security package (`{ !name, default?, parents? }`, ordered like every slot), so a module adds one (a `channel`, a `tenant`) without touching the others; `default` is a mapping over the request scope for endpoints that don't name the dimension, and a grant that doesn't name a dimension matches any value of it, so grants and endpoints written before a dimension existed keep their meaning. **Hierarchies:** `parents` is a pure mapping from a value to its parent values, so a dimension's values form a hierarchy and a grant on a value covers its whole branch; `*` is the top of every dimension. For `resource` it is the kind chain (a new pure function `$func/kind-chain`): entity types form hierarchies through extension, and a grant on `contract` covers every entity type of a kind extending it (`construction`, `general-liability` under `liability`); element ids share one namespace, so kinds and entity types are values of one dimension. For `action` it is the action levels: `write` covers `create`, `update`, `delete` and the transitions, `read` covers `read`, `list`, `search`. An endpoint declares `operation`, a mapping to the dimensions (`{ "area": "entities", "resource": "#.params.entityType", "action": "update" }`), or `public: true`; `validate()` reports an endpoint with neither. The payload may decide which operation a request is (a command or transition named in the body), under two rules: the rule sees `{ params, query, headers, input }`, where `input` is the output of the endpoint's `request` mapping, so what is authorized is exactly what the target receives, never a raw body the target reads differently; and every dimension's inferred type is a closed set (a literal, an enum, `@ref/<kind>`), since a grant can name only values it can enumerate; `validate()` reports an unbounded `string` or `number`. Checks on the data's values (an amount limit, own records only) are not operation identification: they stay in the domain as guards seeing `_ctx.user` and the validated record. **Actors and roles (P20).** A module declares `actor` elements with grants. **Compact grants:** a grant is a box in the space, not a point: each dimension is a value, an array of values or `*` (any value, also when omitted), and the grant permits the cartesian product (`{ "area": "states", "resource": "construction", "action": ["issue", "cancel", "renew"] }` grants three transitions; `{ "id": "underwriter", "kind": "actor", "data": { "grants": [{ "area": ["entities", "states"], "resource": "construction" }, { "area": "entities", "resource": "party", "action": ["read", "list"] }] } }`). `validate()` checks each named value against the closed set of its dimension and its hierarchy nodes where one is known (the transitions of an entity type, the entity types and the kinds they extend). The application declares `role` elements that only list actors (`{ "id": "back-office", "kind": "role", "data": { "actors": ["underwriter", "user-administrator"] } }`, `@ref/actor`); roles hold no grants of their own, so a permission no module offers is an actor of the application's own module. A user holds role names. Domain modules declare actors over their own resources (entity types); generic modules, which don't know the application's resources, declare coarse ones (`entity-reader`, `resource: "*"`) and the ones they own (`user-administrator` in users). Process tasks (R5.3) will be assigned to actors the same way. **Resolution.** Actors and arrays cost nothing at run time: at load, each role's grants are flattened through its actors into a trie with one level per dimension, in the order of the dimensions, whose edges are the named values and `*` (an array is several edges to one subtree; a value with a hierarchy is the edges of its whole branch, expanded at load, which the closed-set rule makes possible since every dimension's values are known then) and whose leaves are the roles, as a bitset, so the leaves reached are joined and checked against the user's roles by bit operations. A request's operation walks it following, at each level, the edge of its value and the `*` edge: at most 2ⁿ paths for n dimensions, in practice few, since only edges that grants created exist; the cost depends on the dimensions, not on the number of actors, roles and grants. The request is permitted when one of the user's roles is among the leaves reached (no principal `401`, no role `403`). A flat index of the 2ⁿ keys (8 for three dimensions) is equivalent and simpler while n is small; the trie keeps lookups cheap as dimensions are added. Branch expansion multiplies the index by the size of the branches, not the lookup. For a dimension whose values aren't a closed set (should the rule be relaxed for one), its branches can't be enumerated at load: the request then expands its value to its ancestors (memoized) and follows each one's edge, at most Π(dᵢ + 1) paths for hierarchy depths dᵢ. **No deny.** Permissions are monotonic: a user's permissions are the union of the grants of their roles' actors, so adding a role or an actor never removes one. Negative assignments are not supported: they would make a role's meaning depend on the user's other roles, need a conflict rule (deny overrides, most specific wins, order), which hierarchies make surprising (an allow on `construction` against a deny on `contract`), let one module's actor revoke what another module's actor grants in the same role (against P20), and keep lookup and explain from stopping at the first granting role. The needs behind deny are covered otherwise: blocking a person is the user's `suspended` state; separation of duties (the creator can't approve) depends on data, so it is a domain guard seeing `_ctx.user` and the record; withdrawing a capability is removing the actor from the role. Should "everything except" be needed, it is an exception local to one grant (`{ "area": "entities", "resource": "*", "except": [{ "resource": ["user", "role"] }] }`): the grant is its box minus the excepted boxes, the union stays monotonic, and the closed-set rule lets the load expand it into explicit edges, so lookup doesn't change and a new entity type is included at the next load; left out until a case needs it. **Static checks.** `validate()` reports a role naming an unknown actor, warns about an actor grant that matches no endpoint operation and an endpoint no actor grants; `bpf explain` shows endpoint → operation → actors → roles, through which hierarchy node a value is granted (`construction` through `contract`), and a role's operations. **Users.** Users are created and changed only through the entity API, a token never creates one, so who may create users is itself a grant (actor `user-administrator`); the first administrator can't come through the API: a migration (`bpf migrate`, which also runs the scripts that create tables) inserts an administrator user, as the system principal through the entity operations, and the app config's `security.actAs` maps the subject of a concrete login to it (`{ "actAs": { "<subject>": "administrator" } }`, `BPF__security__actAs__<subject>`): `authenticated` reads the user whose business key is `actAs[sub] ?? sub`, so the deployment, not an element file, decides who the administrator is, and the migration holds no subject or credential. Why not URL patterns: a policy would depend on the route layout and two endpoints couldn't share an operation. Open: parameterized actors, a generic actor whose resource a role supplies (`{ "actor": "entity-editor", "resource": "construction" }`), left out until needed; how entry points other than HTTP (message consumers) obtain and check a principal. | agreed |
| F21 | **Execution tracing** in a native execution object beside `_ctx`: the path of nodes, operations and slot fills a run took, for logs, debugging and diagrams. | open |
| F22 | **Entity traits (P17).** A record's `data` is a map of traits: `body`, the business data, and every other key (`state`, `versions`, …). `body` is semantically a trait like the others (owned key, written through a command, revisioned, seen by slots and events alike) and structurally special only because every entity has it (`bodySchema`, `create`/`update` on `entity-type`). All traits share one JSONB column and the revision history, so a new trait needs no migration. Rules: one owner per key: `body` is written by `create` and `update`, which carry the other keys over; a trait's key is written only through the trait (`entity-type.trait`). A trait is an `entity-trait` element whose id is its key, with a configuration schema. `entity-type` declares one slot, `traits` (many `{ trait, configuration }`): an entity type uses a trait through a fill on itself, its class or `entity-type`; per trait the most specific fill wins; `validate()` checks the trait, its configuration and repeated uses through the kind's `validate` hook. Declaring trait uses inside the entity type's own element (locality) is a separate concern. A trait initializes its value on `create`; its commands are operations of its own service, exposed by its own endpoints (P16). Changes and events name the trait and the command. Open: whether one trait may derive another's key (versionable keeping `body` as the version valid now). | in progress |
| F46 | **Pure side, against the goals.** The pure side serves data flow between nodes (P3), conditions (guards, `validate` hooks), derived data (slot mappings) and business rules (G1, G10); P5 leaves algorithmic logic to JS pure functions. P3 is met by construction. The language's semantics are settled (`lambdajson-js` 3: strict operands, deep equality, functions with named parameters, typed primitives). What remains in the framework, by owner: **framework packages** (G1, built from primitives by G7, not added to the language): money as decimals with explicit rounding, and pure date arithmetic (add days, compare, period length), as `pure-function` elements. **Core**: checked signatures and `examples` (F11), rule kinds (F12). | open |
| F47 | **Evaluating pure code from the CLI.** `bpf eval <pure-function or element path> <input>` runs a mapping or pure function with a given input and prints the result, so authors and agents try a rule without booting infrastructure or writing a test; declared `examples` (F11) run the same way. | open |
| F29 | **Read-only values beside a middleware chain.** A middleware method sees only what the previous one passes on. Entity interceptors receive `{ operation, input }`; the store write ignores a changed `operation`, but interceptors after the one that changed it see the changed value. Proposal, when a case needs it: the middleware node passes a read-only part beside the chain input. | open |

## Open questions

- Q4: Code generation at load time: should a kind's `load` hook be able to expand an instance into further elements or pipelines, and if so, how does an expansion embed load-time values into the LambdaJSON trees it generates, and is generated code validated against the kinds it targets?
- Q5: Merge semantics for hierarchies: `defaults` merge deeply along the kind chain, with arrays combined by index and no way to remove a key. How does a subkind add a field to an inherited schema or drop one?
- Q6: Contracts that depend on the instance: how an operation's input or output schema refers to `self` (the `body` of `create` is `self.data.bodySchema`), instead of each operation checking it in its implementation.
- Q11: Checked `defaults`: a kind's `defaults` are typed `object` and unchecked, and deep merge is wrong for schemas (`!field` and `field` both survive; `"@id"` strings replace objects; schemas compose with all-of). Options: check them against a partial of the chain's shape (every key optional), added as `<kindId>/defaults`; let the kind declare how each field composes; or keep the plain merge.
- Q12: Specializing instances: kinds extend to any depth, but instances are leaves. Specializing `construction` into subtypes means promoting it to a kind, which breaks every reference to it. Options: kinds only (current); `extends` on instances of the same kind (prototype inheritance: data merges along the instance chain, and fills targeting an ancestor instance apply); or unify kinds and instances.
- Q17: File and folder conventions. Elements carry all meaning (`id`, `kind`, slot fills, `context`), so a path that also means something would be a second, hidden metadata channel that can disagree with the element. **Proposal:** the runtime ignores paths; conventions serve people and tools and are enforced by a lint check, not by semantics. Candidates: organize by feature, not element type; a kind is defined in a file named after it, or id prefixes match the package; a uniform package shape (`elements/*.eson` next to `src/*.js`), with `low` references resolving to modules of the package or its declared dependencies. **Open:** what folder conventions usually stand in for is a package boundary (exports, dependencies, which elements outsiders may invoke or fill slots on; today any element may do both). If wanted, declare it explicitly, in line with author-based binding rights, rather than infer it from folders.
- Q21: Validated solutions: `validate()` runs on demand, never on start. Should a start check that the element set it runs is the one validated (a fingerprint), or is that left to the deployment?
- Q22: Reusable methods with effects. Today a library is a service element whose operations are its methods: a namespace, a contract per method, replaceable through a subkind or binding. A library method gets what it needs through its input, never from the caller's `self` (shared behaviour on `self` belongs in a common base kind). Open: whether a free-standing counterpart of `pure-function` is worth adding (an element with a `signature`, run with its input and the bound context only); decide when the first library shows whether a service element is too heavy.
