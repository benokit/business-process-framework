# Critique

Open improvement proposals and open questions about the framework, measured against the [project goals](project-goals.md) (G*) and [postulates](postulates.md) (P*). IDs are stable so they can be referenced; resolved items are removed (the last version with them is commit `c78a374`). The order and scope of the work is in the [refactoring plan](refactoring-plan.md).

A finding is one of: a **defect** (an input or edit with a wrong or silent result, shown by a test or `validate`), a **violation** of a named G* or P*, **drift** (one fact written in two places that change together) or a **cost** (places touched in fixed scenarios: express a rule, add a state, add an operation, rename an operation, a subtype overrides). Taste (wordy, apart from the type, symmetry) is none of these and changes nothing. An alternative replaces a form only if it wins a counted scenario without losing another; a rejected one is reopened only by a new defect or scenario.

Status: **open** (proposed, not yet decided) · **agreed** (decided, not yet built) · **in progress**.

## Improvement proposals

### Core: language, execution, tooling

| ID | Proposal | Status |
|---|---|---|
| F11 | **Checked pure functions (P5), and trying them from the CLI.** `validate()` checks the arguments of every `$func/<id>` call against its `signature` ([data flow](../implementation/core/README.md#data-flow)); nothing checks them at run time, nor a function's result, nor that a mapping-based function returns what its signature declares. Proposal: check arguments and results at run time; check the inferred result of a mapping-based function against its `output` in `validate()`; run declared `examples` in `validate()`; freeze inputs; a lint configuration for pure modules; a determinism test; optionally an SES sandbox. Purity stays the implementer's responsibility, so the runtime may cache, replay and run pure functions at load time, but never effects. `bpf eval <pure-function or element path> <input>` runs a mapping or pure function (and its `examples`) without infrastructure or a test. | open |
| F12 | **Where logic lives, and what the pure side needs.** (1) Orchestration-level pipelines (named business steps, waits between pipelines, declared extension points) stay data: they enable durability, diagrams, analysis and step extension; steps others may extend are declared as slots, since step names become public API. Fine-grained computation belongs in mappings and pure functions. (2) Glue in mappings; tabular and rule logic in declarative kinds (first candidate: a decision table for rating or eligibility); algorithmic logic in JS pure functions built from small named ones. (3) The language is settled (`lambdajson-js` 3). What remains is a framework package matter (G1, G7): money as decimals with explicit rounding and pure date arithmetic (add days, compare, period length), as `pure-function` elements; and in the core, checked signatures (F11) and rule kinds. | open |
| F21 | **Interpreters.** Built: `traced(run, { skip })` records the spans of a run by decorating the place frames are made, `bpf trace` prints them, and the dry run is the `skip` of `traced` (a skipped `low` node answers `null`, so downstream nodes may fail: the trace shows where). Open: diagrams (a Mermaid sequence from the spans), spans for `forEach` iterations, assertions on spans in tests, recording values for tests; a dry run where operations with `write` or `irreversible` effects are skipped or answered and `read` runs (what a skipped operation returns when its output feeds the next node); an audit interpreter that records every effect reached. | in progress |
| F40 | **Data shapes through pipelines, what remains** (the data flow itself is built: [data flow](../implementation/core/README.md#data-flow)). (1) `entity-event.entityType` stays `string`, since a message may name entity types another application doesn't have (P18), so `entity-search-service.index` still counts every effect class. (2) What a computed `execute` runs, and the outputs of `execute`, `low` and `middleware`, stay unknown. (3) What an `invoke` passes isn't checked against the input contract of its target: `{ "inputMap": { "entityType": "partty", … }, "invoke": "entity-states", "operation": "transition" }` passes `validate()`. | in progress |
| F29 | **Read-only values beside a middleware chain.** A middleware method sees only what the previous one passes on (the entity interceptors that showed it were removed, since nothing filled them; the `middleware` node remains in `http-endpoint`). Proposal, when a case needs it: the middleware node passes a read-only part beside the chain input. | open |
| F48 | **Kind values and settings, what remains**. The type of `$func/settings` isn't inferred, so `validate()` doesn't check paths into it; no warning for a setting no code reads; secret settings (if `explain` ever shows effective values); the `fixed` values of a kind without instances aren't checked against its shape; a data operation marker left in `data` outside a `/merge` isn't reported. | in progress |
| F70 | **A kind sees its own shape ([P24](postulates.md)).** Today the shape of an instance is the all-of of the shapes of its chain and `fixed` is united with the instance's data, so a subkind can only add to its parent's vocabulary, never replace it: `insurance-contract-type`, the demo's amendment types and `entity-type` write whole `traits` configurations as `fixed` or as instance data of the parent's shape, and `fixed-conflict` exists only because kind data and instance data are the same object. Proposal: a kind has one `shape` (its instances' data, which its code sees), an optional `mapping` to the parent's shape, and `fixed` as part of its own shape; no `mapping` passes the data unchanged and the kind has its parent's shape, so a kind that only adds fixed values or operations doesn't change; a subkind that declared a shape beside its parent's (`entity-type`) now declares a mapping, here the identity `#.data`. Counted on the demo's contract types (`insurance-contract-type`: 2 instances, `underwriting-amendment-type`: 3), places touched with today's form / with a mapping of the kind to a vocabulary without the `traits.<key>.configuration` wrappers: add a contract type 1 / 1; add a trait to every contract type 1 (`fixed`) / 1 (a constant of the mapping, merged by `$merge`); rename or restructure a key of a trait's configuration 3 (the kind and both instances) / 1; the same for an amendment type 4 / 1. Built (R3.7) for the amendment types, as the demo of the layering rather than for the count. Nothing is lost in a counted scenario; the gain grows with the instances of the kind, and the costs are not counted places: the kind declares a shape and a mapping, the constants of `fixed` move into the mapping (a mapping that overrides one raises no `fixed-conflict`), and every instance has one more representation to read in `explain`. Built on what exists: an operation's `owner` (a subkind can't redefine an operation, so no subkind calls its parent's implementation) says which level its code sees; `mappingType` with `expected` types a mapping against the parent's shape. Open: (1) the level of `self` in the effect inference of `#.self.data` targets and in the values bound to managed context keys ([context.js](../implementation/core/src/context.js)); (2) validation and `explain` must name the level and the authored path of a problem found in a mapped representation; (3) a mapping result that differs from the parent's `fixed` is a `fixed-conflict` at the kind that declares the mapping; (4) whether a kind's code ever needs the shape itself (`#.kind.shape`). | agreed |

### Delivery and infrastructure

| ID | Proposal | Status |
|---|---|---|
| F43 | **Delivery.** Npm packages, one per module, in a private registry (GitHub Packages), all under one version. The public API is the element ids and contracts (kinds, operation contracts, integrations, schemas, slots): renaming or removing one is a breaking change. An application is an npm project whose `dependencies` are its modules (replacing a module is replacing a dependency, G9; `validate()` lists the integrations left unimplemented), beside its own elements, JS modules and `/uri` files. The server loads the declared modules and what they depend on, never whatever is installed (today it scans the monorepo's `node_modules`). A scaffold (`npm create business-framework`) writes dependencies for the chosen adapters, compose services, a Dockerfile and agent instructions (G8). The application builds its own image; configuration comes from `BPF__` variables, so one image runs everywhere. | agreed |
| F38 | **Index maintenance as a durable ETL.** [entity-search](../implementation/entity/entity-search/README.md) needs two operations: *reindex* (the mapping or settings changed, so every document is derived again) and *recreate* (clear and insert again). Today's `reindex` is a naive recreate: one insert and wait per record, only the first 200, not resumable. A proper one is a durable ETL: pages, recorded progress, resume after a crash, no lost changes while it runs (for example a new index swapped in). Open: whether a durable ETL is a kind outside the core, like durable processes (Q3). | open |
| Q3 | **Durable processes outside the core (P14).** Waits happen only between pipelines, so the core needs no execution log or replay; a durable process is a kind built from entity states, message consumers and delayed messages. Given: atomic state change and messages (outbox), stable `messageId`. Missing: delayed delivery (the only timer) and routing a message to its process instance (a publisher-chosen correlation key). Open: whether delayed delivery is a messaging capability or a scheduler kind. Versioning running processes is the process kind's concern. | agreed |

### Entities

| ID | Proposal | Status |
|---|---|---|
| F67 | **Open points left from the implemented designs.** (1) Historic reads: a read at a past revision is judged by the ownership that revision had, so a user whose region the record left can still read what it was then; judging by the current ownership needs the current record beside the past one. (2) Nothing detects that an ownership rule changed since the last backfill; the application adds a migration with a new id. (3) Trait or slot. Direction of knowledge decides: what an entity type (or its class) names and configures is a trait, which brings configuration and behaviour (`initialize`, `derive`, `view`, and the hooks `guard` and `react` to come) and may persist a value under its key, or nothing; what something else contributes to the entity type (application policy, integration, a wrapper of the write) is a slot fill. The business key is the trait `business-key` (`identity`), configured by the entity type; the guard of `state` is a hook of the trait, not a fill. To settle: how a trait without a value is identified and merged (the key as a name only), the order of trait hooks against fills, and the effect bounds of hooks. (4) Whether one trait may read another's configuration, reachable by key. Decided: reading a specific trait goes through an interface (an operation or an attribute of its kind, as `identity` is for the business key), never through a path such as `data.ownership`, so that a trait can sit under another key or inside another trait; done for the readers of other packages (`ownership` in row access and search, `state` in state-permissions, oauth and the amendments, `body` in oauth and the amendments); left, as their own: a trait reading its own key (states, ownership, the amendment link and ledger), and the users service reading the body of its own entity type. (5) State-based control covers only the operation's own entity: a process changing records of another entity type is judged by its own operation, and a `state` dimension on `query` grants is rejected. | open |
| F64 | **The storage format of a trait is not versioned.** A plain body and a timeline are different JSON, so turning `versioned` on, or putting another trait under a key (R6.15), leaves existing records in the old format and their reads fail. Ownership has a one-off backfill but there is no general "the storage format of this trait changed, migrate it". Proposal: a trait operation `migrate` (old value and configuration to the new value), run for every record of an entity type as a migration, and a `validate()` check or documented rule that a change of the trait or its storage-relevant configuration comes with one. | open |
| F71 | **The derivation of traits is a fold with several channels; it should be one worklist to a fixed point.** Today the `derive` hooks run once, in the implicit key order of `$func/entity-traits` (kind chain, then the entity type's data, then fills); a derive returns a command for its own key and optionally `operations` on other traits, which run at once, do not see one another and cannot be chained; a `null` result cannot request operations; a derive sees only the record, not what changed; its commands are written but missing from the change that reactions and events see (the README says they join it); and `derive` has no effect bound, unlike guards (read, trace) and reactions. Proposal: one queue of trait operations; each iteration runs the next operation on the current value of its trait and applies its command; a derive returns an ordered list of operations (empty for none; its own value is an operation on its own trait), so a trait needs no value to trigger another. The derives are consulted one at a time, in trait order, and the operations of the one consulted run before another is consulted: requests of several derives queued together would be computed on a state that an earlier one changes, and the stale one would overwrite the right value (found when implementing R6.36). (1) The keys a derive reads are declared by the author of the entity type, in the use of the trait (`dependsOn`, beside `configuration`, which stays the trait's own schema), not by the trait. A command applied to such a key, whether or not the value changes, makes it run again, and the dependencies are the only ordering mechanism: if the order between two derives matters, one reads what the other produces. The stable trait order breaks ties for reproducibility only. `validate()` reports a dependency on a key the entity type lacks. A derive with no dependency runs on the first iteration only, and the operation `derive` of the entity type, which has no command to start from, seeds every derive once. (2) Termination is a runtime limit on the number of iterations; exceeding it is an error that carries the sequence of commands; the limit is an application setting of the kind that runs the fold (the `settings` of the kind, overridden by `app-config` and the environment). (3) A derive receives `{ entityType, key, configuration, record, command }`, the command just applied, its record with every earlier command applied. (4) The commands of a write are the executed operations in order: guards see the seeds, reactions and events the whole sequence. (5) A derive is bounded to `read` and `trace`, and so is every trait operation a derive may request (an operation whose output is a trait command), checked statically by `validate()`; a plan operation may still write. (6) Operations requested on one trait by derives that do not read one another must commute; nothing orders them. (7) Guards run twice: on the request (before any derivation, as today: access and visibility are decided before any work, so a caller never learns more from a derive failure than from `forbidden`) and on the result (after the derivation, before the transaction: the full sequence of executed commands, `before` against the final `after`). The result guards are the slot `resultGuards` of the entity type, as `requestGuards` (the former `guards`, renamed so that the two read as a pair) in every respect but the moment (a `phase` on the change, selected by the guards and the fills, would have needed a second selector in the core's slots, and every existing guard would have had to opt out of the result run); the traits' `guard` hook stays on the request. Refusing on the result needs no rollback: nothing is written yet, and guards only read and trace. This guards what a derive adds, such as the ownership a rule computed or a transition it asked for, which no guard sees today. (8) A derive must be idempotent: a command on a key it reads, its own included, triggers it again, and it returns no operations when its value is already right; the iteration limit is the only guard against a loop. (9) With several commands on one key, `$func/change-command` gives all of them as a list (today it returns the first match, while the store keeps the last), so a reaction decides among them. (10) The preview of a plan (`commit: false`) runs the whole fold and the guards of both phases, and returns the commands of the whole write and the entity after them, so it shows what the write would do; today it builds the entity from the operations of the plan alone, without the derivation. A preview that cannot reproduce the derivation is not kept. | agreed |
| F72 | **`dependsOn` is checked only for existence (drift).** The code of a derive and the entity author's `dependsOn` must agree, and `validate()` reports only a key the entity type lacks ([traits.js](../implementation/entity/entities/src/traits.js)). Scenario: an ownership rule reads `body` and `state`, `dependsOn` lists `body`; a state transition never recomputes the ownership and nothing reports it. An empty list means "always run", so only an incomplete list is unsafe. Proposal: `validate()` reports a key a derive reads (the paths its mapping reads, from the data flow) that `dependsOn` doesn't list. Not checked whether the data flow can see the reads of every derive. | open |
| F73 | **Validation errors of several fills overwrite each other silently (defect).** The errors of the `validations` fills are united with `$merge`, so two fills (a class's and an entity type's) that name the same error overwrite each other with no report ([entity-validations](../implementation/entity/entity-validations/README.md)); the README states it, the result is still silent. Options: errors namespaced by the id of the fill, or a list per name. | open |
| F74 | **Row access refuses by a reaction, though `resultGuards` exists.** `refuse-uncovered-results` is a `reactions` fill: it writes, then throws and rolls back ([entity-row-access](../implementation/entity/entity-row-access/README.md)). R6.39 built `resultGuards` for this case (a derived ownership the actor may not give), which refuses before any write. Two mechanisms for one job, and the README of the package still describes the reaction. Proposal: move the fill to `resultGuards` (`on` `create` and `trait`). | open |
| F75 | **Correcting a version after amendments.** The stack form of amendments is by design ([entity-amendments](../implementation/entity/entity-amendments/README.md#why-a-stack)): the side effects of an applied amendment (invoices, payment orders) can't be compensated for an arbitrary retroactive change, so a version dated before the last is `conflict`, only the latest is reverted, and `update` is `conflict` once amended. Retroactive changes are only technical corrections without business significance. Open, narrow: such a correction (a typo in the first version) can't be made after an amendment, short of reverting every later one, which compensates the effects the design avoids. Options: a field without business significance in a trait that isn't versioned (nothing new in the core; shown by the test 'a trait beside a versioned body' in [entities](../implementation/entity/entities/test/entities.test.js): a trait of its own, here the handler of a contract, changes after an amendment and is read at any `at`; a second instance of `plain-body-trait` is not possible as it is: a quick try reported `invalid-element` (cause not investigated; `update` is public in both, and `record-body` finds the first `body-trait`), so such a trait declares a public operation of its own name), or a correction operation that carries a patch across all versions, guarded to fields marked as non-significant. Decide by a counted scenario (how often such a field sits in a versioned body); until one exists, no change. | open |
| F76 | **Relations after the delete of a target (by reading, not tested).** Both foreign keys of `entity_relations` cascade, and a rule's targets must exist when it runs, so after the target is deleted the next unrelated write of the source recomputes the relation and fails with `not-found`. Next: a test that confirms or refutes it; if confirmed, decide whether a delete of a referenced entity is refused, or a missing target is dropped. | open |
| F77 | **Drift in the entity READMEs.** The schema `entity-operation` is described twice in [entities](../implementation/entity/entities/README.md) (after the operations table and under "Public and private operations") with different wording; a broken bullet in [entity-states](../implementation/entity/entity-states/README.md) ("-  a record no longer at `revision`…"). Keep one owner of each fact. Also: `bpf validate . ../demo` reports `duplicate-element: entity-reader-actor` while `bpf validate` alone is valid (not investigated). | open |

### Time

| ID | Proposal | Status |
|---|---|---|
| F54 | **An abstract "now" for the application, not for the framework ([P23](postulates.md)), and the facts stored before it.** (1) A versioned body reads the last version, which is not the version in force today once a later-dated one exists, and the framework must not know the date. Proposal: a reference date as a context key (`validAt`) managed by one kind, bound by the layer that controls the request (security layer, or a setting such as "today", "last version" or a fixed date for a replay) and read by `read` as the default of `at`; without it nothing changes. Open: who binds it and from what (setting, header, claim), whether it feeds search and relations, whether it carries a time zone. (2) Ownership is derived at write time from the last version and stored once, so a future-dated amendment that moves a contract to another region changes access today; with `validAt`, reads become time-dependent while the stored fact stays fixed, and the search filter and the guards can disagree. The same holds for every fact a trait derives and stores. Options: derive per version (the fact becomes a timeline), or declare that a stored fact always describes the last version and access is not time-dependent. | open |

## Open questions

- Q4: Code generation at load time: should a kind's `load` hook be able to expand an instance into further elements or pipelines, and if so, how do expansions embed load-time values into LambdaJSON trees, and is generated code validated against the kinds it targets?
- Q6: Contracts that depend on the instance: how an operation's input or output schema refers to `self` (the `traits.body` of `create` is checked against `self.data.traits.body.schema`), instead of each operation checking it in its implementation.
- Q17: File and folder conventions. Elements carry all meaning, so a path that also means something would be a hidden second metadata channel. **Proposal:** the runtime ignores paths; conventions serve people and tools and are enforced by lint: organize by feature; a kind in a file named after it, or id prefixes matching the package; a uniform package shape (`elements/*.eson` next to `src/*.js`). **Open:** what folders usually stand in for is a package boundary (exports, which elements outsiders may invoke or fill); if wanted, declare it explicitly, in line with author-based binding rights.
- Q21: `validate()` runs on demand, never on start. Should a start check that the element set is the one validated (a fingerprint), or is that left to the deployment?
- Q22: Reusable methods with effects. A library is a service element whose operations are its methods (a namespace, a contract per method, replaceable through a subkind or binding), getting what it needs through its input, never from the caller's `self`. Open: whether a free-standing counterpart of `pure-function` (a `signature`, run with its input and the bound context) is worth adding; decide when the first library shows a service element is too heavy.
