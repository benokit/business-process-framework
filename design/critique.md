# Critique

Open improvement proposals and open questions about the framework, measured against the [project goals](project-goals.md) (G*) and [postulates](postulates.md) (P*). IDs are stable so they can be referenced; resolved items are removed (the last version with them is commit `011bc91`).

Status: **open** (proposed, not yet decided) · **agreed** (decided, not yet built) · **in progress**.

---

## Improvement proposals

| ID | Proposal | Status |
|---|---|---|
| F7 | **Declared effects.** Effects bottom out in `low` nodes, which today may appear in any pipeline. Proposal: effect kinds declare a contract and an effect class (read / write / external / nondeterministic), and `low` appears only as the implementation of a declared effect; `validate()` rejects any other use. This is the single place to classify effects, check their contracts and attach interpreters. The payoff is **swappable interpreters**: production, a test interpreter with stubbed effects (an entity flow tested with no database or broker), dry run, audit, replay. Effect classes also let `guards` be checked as side-effect free. | agreed |
| F9 | **Pipeline granularity.** Orchestration-level pipelines (named business steps, waits between pipelines, declared extension points) are worth keeping as data: they enable durability, diagrams, analysis and step extension. Fine-grained computation is not: it belongs in mappings and pure functions. Steps others may extend must be declared (slots), because step names become public API (fragile base class). Precedents: Step Functions and BPMN (data), Temporal (code plus replay). | open |
| F11 | **Checked pure functions (P5).** `pure-function` elements declare a `signature`, which isn't checked. Proposal: check arguments and results against the signature; run declared `examples` in `validate()`; freeze inputs; a lint configuration for pure modules; a determinism test; optional SES sandbox. Since purity is the implementer's responsibility, the runtime may then cache, replay, version and run pure functions at load time, but never effects. | open |
| F12 | **Place each kind of logic where it fits:** glue in mappings; tabular and rule logic in declarative kinds (decision tables, lookups); algorithmic logic in JS pure functions. Build large logic from small named pure functions. First candidate: a decision table kind for rating or eligibility. | open |
| Q18 | **Static checks of code**, run by `validate()` over the loaded elements, on demand. Code is found only through `@method` and `@mapping` positions in shapes, so new kinds are checked as soon as their shapes say where their code is; a method's author is the element whose data holds it. Level 1, structure: each node matches exactly one node form; unknown keywords; `next` outside a middleware method or wrapper implementation; `outputKey: "_ctx"`. Level 2, references and rights: literal `invoke` targets, `instanceOf` kinds and operations exist; slot names in `$func/slot-values` are declared; `low` modules and functions resolve; `withContext` keys are managed by the author's kind; `#._ctx.<key>` paths are read or managed by the author's kind. Computed targets (`"invoke": "#.self.data.broker"`) are checked at run time only. Data flow (shapes through `outputKey`s against target inputs) stays with the run-time contract checks. `bpf-validate` runs in CI. | in progress |
| Q19 | **Database independence below the elements.** Packages reference `database`, `message-broker`, `message-outbox` and `search-engine` by kind, but `transaction`, `transactional-outbox` and `sequence-generator` import the PostgreSQL pool in JS, so they work only with `postgresql-database`. Proposal: they reach the database through its operations (`execute`, plus session operations for transactions), or the transaction kind becomes part of the database abstraction. Models stay SQL fills on `postgresql-database`, since they are written in its language. | open |
| Q3 | **Durable processes outside the core (P14).** Waits happen only between pipelines, never inside one, so scoped context and `next` never cross a wait and the core needs no execution log or replay. A durable process is a kind built from entity states, message consumers and delayed messages. Already given: a state change and its messages commit atomically (outbox); a stable `messageId` lets consumers be idempotent. Missing: delayed or scheduled delivery (the only way to express a timer), and routing a message to its process instance (a correlation key chosen by the publisher). Open: whether delayed delivery is a messaging capability or a scheduler kind. Versioning running processes is the process kind's concern (pin the definition per instance). | agreed |
| F20 | **Security layer.** `authenticated` binds the principal when a token is valid, and nothing requires one: an endpoint without a token runs with no `user`. Consequence: `entities-http` serves every entity type to anyone, including `user` records with their `passwordHash`, and `PUT` can change their `roles`. Proposal: a permission model enforced where effects happen (entity operations), deny by default, with the principal checked against the operation and the entity type; endpoints declare whether they need a principal. | open |
| F21 | **Execution tracing** in a native execution object beside `_ctx`: the path of nodes, operations and slot fills a run took, for logs, debugging and diagrams. | open |

## Open questions

- Q1: Who authors declarations, and when do they change? If only developers author them, typed TypeScript objects (still plain data) may be simpler than `.eson`; JSON plus LambdaJSON is justified for non-developer, per-tenant or run-time-changed definitions. Decide this deliberately.
- Q4: Code generation at load time: should a kind's `load` hook be able to expand an instance into further elements or pipelines, and if so, how does an expansion embed load-time values into the LambdaJSON trees it generates, and is generated code validated against the kinds it targets?
- Q5: Merge semantics for hierarchies: `defaults` merge deeply along the kind chain, with arrays combined by index and no way to remove a key. How does a subkind add a state or drop a transition?
- Q6: Contracts that depend on the instance: how an operation's input or output schema refers to `self` (the `data` of `create` is `self.data.dataSchema`), instead of each operation checking it in its implementation.
- Q11: Checked `defaults`: a kind's `defaults` are typed `object` and unchecked, and deep merge is wrong for schemas (`!field` and `field` both survive; `"@id"` strings replace objects; schemas compose with all-of). Options: check them against a partial of the chain's shape (every key optional), added as `<kindId>/defaults`; let the kind declare how each field composes; or keep the plain merge.
- Q12: Specializing instances: kinds extend to any depth, but instances are leaves. Specializing `construction` into subtypes means promoting it to a kind, which breaks every reference to it. Options: kinds only (current); `extends` on instances of the same kind (prototype inheritance: data merges along the instance chain, and fills targeting an ancestor instance apply); or unify kinds and instances.
- Q17: File and folder conventions. Elements carry all meaning (`id`, `kind`, slot fills, `context`), so a path that also means something would be a second, hidden metadata channel that can disagree with the element. **Proposal:** the runtime ignores paths; conventions serve people and tools and are enforced by a lint check, not by semantics. Candidates: organize by feature, not element type; a kind is defined in a file named after it, or id prefixes match the package; a uniform package shape (`elements/*.eson` next to `src/*.js`), with `low` references resolving to modules of the package or its declared dependencies. **Open:** what folder conventions usually stand in for is a package boundary (exports, dependencies, which elements outsiders may invoke or fill slots on; today any element may do both). If wanted, declare it explicitly, in line with author-based context rights, rather than infer it from folders.
- Q21: Validated solutions: `validate()` runs on demand, never on start. Should a start check that the element set it runs is the one validated (a fingerprint), or is that left to the deployment?
