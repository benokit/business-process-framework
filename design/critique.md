# Critique

Claude's evolving critique of the project, measured against [project goals](project-goals.md) (G*) and [postulates](postulates.md) (P*). Updated as the discussion evolves; IDs are stable so they can be referenced.

Status: **open** (proposed, not yet decided) · **agreed** · **revised** (position changed during discussion; see [Revisions](#revisions)).

Last updated: 2026-10-17.

---

## A. Current implementation

**Summary:** data composition and infrastructure are solid; there is no first-class *abstraction* mechanism. Composition runs through a global registry plus `kind` naming conventions, which undermines G3–G6.

**What works:** small runtime (~670 lines), uniform element model, `execution-node-template` (language extension), `injection` (IoC), solid entity storage (optimistic concurrency, history, relations, outbox, search). Nondeterminism (clock, random, sequences) is already treated as an effect.

## B. Foundation positions

| ID | Position | Status |
|---|---|---|
| F1 | **Data, schema and service are not peers.** Schema and service are data plus a built-in interpreter (validator, executor). The hard-coded kinds in [elements-registry.js](../implementation/runtime/src/elements-registry.js) are the same pattern. | open (re P2) |
| F2 | **Proposed minimal core:** values · names and scope · abstraction and application · kind definitions · effect boundary. Schema is the contract language of these, built in for bootstrapping. | open (re P2) |
| F3 | **Abstraction is the missing primitive.** It means parameterized elements and their instantiation. Service methods, pure functions, middleware and entity types are all instances. | open |
| F4 | **Kind definitions:** a `kind` element declares *shape* (schema), *slots* (named, schema-typed, with cardinality and phase), `extends`, and *meaning* (expansion or interpretation). Slot fills are explicit (target + slot), not encoded in `kind` strings. Test: `entity-type`, `middleware` and `service` should be definable in `.eson` with no new runtime code. | open |
| F5 | **Two phases.** Composition (kinds, slots, expansion) happens at load time and produces plain, resolved, inspectable elements. Run time only executes. Programs are static: no construction of pipelines at run time. Models: Lisp macros, the Nix module system. | open |
| F6 | **Effects as data (P3) is sound.** Its value is **swappable interpreters**: production, test (stubbed effects), replay/durable, dry run, audit/authorization, transaction/retry. A restricted pure language guarantees purity by construction; JS can't. | agreed |
| F7 | **Enforce the P3 boundary:** effect node kinds are declared with contracts and an effect class (read / write / external / nondeterministic). No `$low` in expressions (it's unused today anyway). Build a test interpreter early, to prove the boundary holds. | open |
| F8 | **`_ctx`: scope bindings, don't mutate.** Mutating `_ctx` as an effect (P4) is not a purity violation, but it is a data-flow channel outside P3's mapping boundary. Proposal: `withContext: {…}, do: […]` binds values for a subtree only; nothing flows back up. `inTransaction`, the JWT middleware and correlation all fit this pattern. The transaction code already does it by hand ([transaction-impl.eson](../implementation/infrastructure/transaction/elements/transaction-impl.eson)). Contracts may declare required context keys. Handles are visible only to effects; expressions see context data as read-only values. **Agreed and applied** in [examples/f18](examples/f18/README.md#scoped-context-f8): `_ctx` is read-only and flows down only (`outputKey: "_ctx"` is a load error); `withContext` binds for its block, which sees the enclosing context; `next` carries the `_ctx` current where it is called, so a middleware binds for what it wraps; `execution-node-wrapper` (a subkind of `execution-node-template`; the kind, not a flag, selects how it runs) is a middleware around the pipeline written as the keyword's value, so `inTransaction` is defined in data, keeps the caller's context and joins an enclosing transaction; the root `_ctx` is created only per request and at startup. Open: declared context keys (schema and owner per key). | agreed (re P4) |
| F9 | **Pipeline granularity.** Orchestration-level pipelines (named business steps, waits, overridable points) are worth keeping as data: they enable durability, diagrams, analysis and step overriding. Fine-grained statement-level pipelines are not. Overridable steps must be declared, because step names become public API (fragile base class). Precedents: Step Functions and BPMN (data); Temporal (code + replay). | revised |
| F10 | ~~Expression syntax~~ (text expressions embedded in strings, plus a compiler). **Rejected by the user:** strings don't scale in JSON, complex expressions are unreadable on a single line, and no new compiler is wanted. LambdaJSON trees remain the only form of pure expressions. | dropped |
| F11 | **Complex pure functions (P5).** `pure-function` elements with a JS `implementation`, a signature (schemas) and `examples`, in the same namespace as expression functions. Arguments only, no `_ctx`. Layered checks: frozen inputs, lint, output schema, determinism test, property tests; optional SES sandbox. The runtime may cache, replay, run at load time and version pure functions, but not effects. | open (refines P5) |
| F12 | **Place each kind of logic where it fits:** glue → expressions; tabular/rule logic → declarative kinds (decision tables, lookups); algorithmic logic → JS pure functions. Build large logic from small named pure functions. | open |
| F13 | **`low` is the primitive effect** (agrees with P4). Every effect bottoms out in it. Rule: `low` appears only as the implementation of a declared effect or service contract. That is the single place to classify effects, check contracts, and attach interpreters. | agreed |
| F15 | **Data is the primitive representation, not the primitive element.** Composition (`/ref`, `/merge`, `/literal`) is not a property of data; it is a minimal load-time composition language ([data.js](../implementation/runtime/src/data.js)). Layers (revised by F17): **value** (native) → **data composition** (native: `/ref`, `/merge`) → **element** `{id, kind, data}` (native) → **kind** (defined; this is where abstraction lives). The single fixed point (the kind of `kind` is `kind`) is a bootstrap axiom; the schema validator is native because `kind` needs it. Data, schema and service become the first defined kinds. | open (refines F2, P2) |
| F17 | **The kind is the abstraction.** An element applies its kind: `data` is the argument, and the kind's meaning (interpretation or expansion) is the function. Parameterization therefore needs no functions inside data. Data composition stays `/ref` and `/merge`. LambdaJSON belongs to run-time code positions and to kind meanings (pure functions in LambdaJSON or JS, F11). Evidence: every use of `/data` in the repo is `/ref` (about 12) or `/merge` (once). The real repetition is solved by shape and factoring: a middleware declaration targeting several methods (11 near-duplicate elements today), and `call` + `inputMap` for entity-service's 6× block. | open (supersedes F16, refines F3, F15) |
| F18 | **Behaviour belongs to the kind** (answers P2's open question). Invoking an element dispatches to its kind, which receives the element as `#.self`. A kind declares **operations** (interface + implementation; closed), **lifecycle** (`load`: pure validation and expansion; `start`/`stop`: effects) and **slots** (open behaviour filled by other elements, called from operations). Classes are kinds with `extends` (replaces A2). Operations are a primitive property of the kind, invoked through an instance (P8); there is no `service` kind (P10): singletons are a kind plus one instance holding their configuration (`password-hasher` / `password`, `schema-registry` / `ajv`), and extra operations for one entity type need a subkind (`user-account`). Kinds may provide `defaults` (formerly `instanceDefaults`), merged under each instance's data. Worked example: [examples/f18](examples/f18/README.md). Lifecycle phases, each run for all elements before the next: **`load`** (make elements known to in-process subsystems such as AJV `addSchema`, `$func` and keywords; no I/O and no validation; replaces the registry `switch`; instance shape checks run natively after all load hooks) → `start` → `stop`. AJV compiles each schema lazily, at most once, on its first validation (`getSchema`). Native bootstrap: pipeline executor, one AJV instance (the `ajv` instance of `schema-registry` with operation `add`, and `schema-validate` by id; `schema` itself is a defined kind with `validate`/`toJsonSchema` operations, P7). Inline schemas get ids at `load`: contracts as `<owner>/<op>/input|output`, instance schemas such as `<id>/dataSchema`. Also native: the `kind` kind (its `load` registers kinds),. In a schema, `@<kindId>` refers to that kind's shape, which replaces the meta-schemas in `core.eson`. Replaces four ad-hoc mechanisms: the registry `switch`, bootstrap special cases, `executeService` (doesn't check kind), and entity-service's convention lookups. **Fixed point lifecycle:** `kind` has its own `load` hook (structural checks via `check-kind`; adds its shape as `<kindId>` and its operation contracts to AJV). It runs for every kind, including `kind` itself, so the driver has no special case; resolving a kind only reads data, so there is no regress. ``, node keywords, injections and slot fills become **lazy native views** over the registry, not registrations, which keeps load hooks order-independent and removes the registry `switch`. An element without a kind has kind `data` (the trivial kind); an undefined kind is a load error (A1). | open |
| F19 | ~~**One execution property per kind.**~~ **Dropped** at the user's decision: operations are a primitive property of the kind again (P8), invoked through an instance; there is no `service` kind (P10). Original text: Operations aren't part of `kind`. A kind has a single `execute` pipeline that handles every invocation of its instances. Native rule: `invoke(x, op, input)` runs the nearest `execute` along x's kind chain with `#.self = x` and `#.input = { operation, input }`; if there is none, x can't be invoked (P10). `service` provides the operation table: its `execute` dispatches over `#.self.data.operations` and checks per-instance contracts. Kind-wide operations become `defaults.operations` (e.g. `entity-type extends service`), and instances add their own by merge (P6, P8). This needs `#.self` scoped to the invocation like `_ctx`. Open: overriding default operations (Q7), calls to the parent's `execute`, and `kind`'s own reflection operations. Kind shape shrinks to `extends`, `shape`, `defaults` (formerly `instanceDefaults`), `slots`, `lifecycle`, `execute`. Kinds whose instance data can't host an operation table define `execute` directly: `schema`'s data is the schema itself, so it uses a `switch`. Applied in [examples/f18](examples/f18/README.md). | dropped |
| F16 | ~~**One pure language in both phases.**~~ **Dropped:** no realistic use case in the codebase, and `/eval` is as much noise as `/data`. Original text kept for history:  Unify `/data` (load time) with LambdaJSON (run time). The phases differ only in available primitives: element references at load time, context at run time; effects only in run-time nodes. Reference cycles: reject them (simpler than fixed-point semantics). Refinements: (a) **mode by position:** run-time keyword positions (`set`, `inputMap`, `if`, …) are code, as today; `pure-function` data is code. Element `data` is literal by default, and code appears there only inside `{ "/eval": <tree> }`. This replaces `/ref`, `/merge` and `/literal` (`/ref` may stay as shorthand). Abstraction means applying a pure function in `/eval`: `{ "$func/id": args }`. Inside code, literals that contain `#` or `@` strings need `$literal`, so prefer named data elements plus `$ref`. This keeps CJSL strings (`@date`, `$data#1`) safe, with no migration of existing pipelines. (b) `ref` is pure in both phases, because the registry is immutable after load. Static refs are checked at load time; dynamic refs are allowed but can't be checked. (c) Implementation reuses LambdaJSON `compile` with a `$ref` primitive and a cycle guard; no new compiler. ## Open questions

- Q1: Who authors declarations, and when do they change? This decides F14.
- Q2: Is there a primitive below data, schema and service (P2)? Proposed answer: F2, refined by F15 and F17.
- Q3: Do business processes require durable execution? If so, F9 and F11 versioning become core concerns.
- Q4: Code generation at load time (F4 expansion): how an expansion embeds load-time values into the run-time pipelines it generates, as LambdaJSON trees, and whether generated code is validated against the kinds it targets.
- Q5: Merge semantics for hierarchies (F17, A4): lodash deep merge combines arrays by index and can't remove keys. How does a subtype add a state or drop a transition? Settle this when R4.2 needs it.
- Q6: Contracts that depend on the instance (F18): how an operation's input or output schema refers to `self` (e.g. `create` input `data` is `self.data.dataSchema`).
- Q7: Inheritance along `extends` (F18): can subkinds override operations, or only fill slots? Slots only is more robust; overriding is more flexible. The example assumes subkinds may *add* operations and slots but not override them.
- Q8: Order of `start` hooks (F18, A9): declared dependencies between lifecycle hooks, not ordering numbers.
- Q9: Dynamic invocation (F18): may `invoke` take a run-time element id (`POST /entities/:entityType`), or does each kind mount its own routes in `start`?
- ~~Q10~~ (decided: **yes**, P11). A package declares the slot with a `slot-declaration` element (`{ target, slot, cardinality, input, output }`), inherited like the kind's own slots. Because the kind's operations don't call it, the package also provides the call site, usually a fill of an existing slot. Example: [examples/f18/06-entity-relations.eson](examples/f18/06-entity-relations.eson), which replaces the `entity-rule/relations/{type}` convention and the ordering-75 middleware. Original: Adding slots to a kind you don't own (F18): relations and search indexing extend `entity-type` from other packages today. Should packages be able to declare new slots on an existing kind (mixins), or must the kind own all of its slots?
- Q11: `instanceDefaults` (F18): default arguments of the kind as abstraction (F17), but a hidden second merge beside P6, implicit when reading an instance, and wrong for schemas (`!field` vs `field` keys both survive a deep merge; `"@id"` strings replace objects; schemas should compose with allOf `data#&`). Shape: a deep partial of the combined chain shape, derived by removing `!` from every key; added to AJV as `<kindId>/defaults` and checked after load (the example's `"object"` leaves it unchecked). The instance's own `data` then becomes a partial too: only the merged result is complete. Options: keep it as P6 merge; let the kind declare how each field composes; or drop it.
- Q12: Specializing instances (F18, G4): kinds extend to any depth, but instances are leaves. Specializing `construction` into subtypes means promoting it to a kind, which breaks every reference to it. Options: kinds only (current); `extends` on instances of the same kind (prototype inheritance: data merges along the instance chain, and slot fills targeting an ancestor instance apply); or unify kinds and instances.
- ~~Q14~~ (resolved by P8: kind-wide operations live in the kind's `operations` again). Original: Where kind-wide operations live (F19). In the examples they are `entity-type.defaults.operations`, because `service.execute` reads `#.self.data.operations` and `defaults` is the only way a kind contributes to instance data. That's awkward: behaviour is stored as an overridable default, instances can replace it by merge (Q7), and the table and its contracts are copied into every instance. Alternative: the kind defines its own `execute` (a `switch` over its operations, as `schema` does), and the `default` case uses a native **parent call** (`{ "parent": true }`: run the next `execute` up the chain with the same `#.self` and input), which reaches `service.execute` for instance operations such as `user.set-password`. This keeps behaviour in the kind, makes accidental overrides impossible, and `defaults` means default data again.
- Q15: Slot inheritance (F18). Declarations are a union along the kind chain, add-only: one owner and one definition per slot, no redeclaration. Fills are selected, never merged. For cardinality `one` the most specific target wins (override); for `many` all fills run from general to specific (accumulation). Gaps: (a) two fills on the same target, which for `one` should be a load error and for `many` run in hidden load order (A9 again), so they need declared ordering (`after: "<fillId>"`) or a guarantee that order doesn't matter; standard patterns: registration order, numeric priority (today's 50/75/100; avoid), named phases (slots already are this), relative `before`/`after` constraints with a topological sort, order-independence by design (observers and checks, as in Kubernetes validating webhooks), explicit composition by the owner (conflicts with P11). Proposal: a `many` slot declares that its fills are independent (the default; guards as pure checks that collect errors, enforceable with F7 effect classes), real dependencies use `after: ["<fillId>"]` with a topological sort (cycles are load errors, ties broken by fill id, never load order), and two `one` fills on the same target are a load error; on weights vs. phases: weights can encode phases (ranges) and are finer-grained, but they lose the owner-defined meaning of a boundary, use a global number line that independent packages collide on, record dependencies only implicitly (101 "because events are 100"), over-specify a total order, and can't be checked; if weights are wanted, scope them per slot, as a tie-break within one phase; where phases are defined: a phase is a slot. Its existence, cardinality and ordering policy are in the slot declaration; its contract is a schema; its position relative to other phases is where the owner's operation calls `{ "slot": … }` (owned by the kind, and derivable by static analysis since programs are static, F5); order within it is `after` on fills; (b) no opt-out from an inherited `many` fill (like Q5); (c) slot contracts are declared but not registered or checked: they should be added as `<kindId>/slots/<slot>/input|output` and checked by the slot executor (as A6 is for operations). **Recommendation:** slots as phases positioned by the owner's operation; no numeric weights; fills of a `many` slot independent by default and run in deterministic fill-id order (never load order); real dependencies as `after` and `before` (revised: `before` is needed under P11, because a package may have to run ahead of a fill it doesn't own, such as an authorization guard that must say "forbidden" before a business guard's message reveals the contract's state (an earlier audit example was wrong: a guard running *before* the throwing one sees the attempt, not the rejection); `X before Y` is normalized to `Y after X` into one graph per slot, and the resolved order is shown by `describe` or a dump, because predecessors are no longer listed on the fill itself), topologically sorted, with unknown ids and cycles as load errors; plus absolute position (added at the user's request): `position: "first" | "last"` puts a fill in a band ahead of or behind all unpositioned fills without naming any, because naming a fill to express a requirement of one's own (the authorization guard naming the draft guard) leaks an unrelated fill into its definition; bands are edges in the same graph, so several `first` fills keep the base order among themselves and an `after`/`before` contradicting the bands is a cycle error; for middleware `first` is outermost; not allowed on `one` slots; two `one` fills on the same target are a load error; no opt-out mechanism (use a data flag the fill checks, or a `one` slot with a class default); register and check slot contracts now; later, enforce side-effect-free `guards` with F7 effect classes. Applied in [examples/f18](examples/f18/README.md#slot-order-and-contracts).
- ~~Q16~~ (decided: **yes**, P12; applied in [examples/f18](examples/f18/README.md#slots-are-data-the-owner-decides-how-values-are-used)). Slots are typed contribution points `{ cardinality, value }`; fills contribute a `value`; `$func/slot-values` reads them. The old `slot` node is gone: owners use the values with ordinary nodes (`set`, `execute`, `forEach`) or with a native **`middleware`** node (a list of methods plus an `action`; each method receives `next`, so it can act before and after, change input or output, short-circuit or retry). `middleware`/`next` are native because a continuation in data needs quoted pipelines (A5). Order for middleware runs outside to inside. Per-call contracts of method slots are now the consumer's; fill values are checked against `<owner>/slots/<slot>` after load (revises Q15c). Original: Slot fills as data (F18). Today a fill is always a method (`implementation`), a leftover of slots replacing middleware. Proposal: a fill contributes a `value`; the slot's declaration decides what that is. With `value` (a schema), fills provide data, and `{ "slot": … }` returns the value (`one`) or the values (`many`). With `input`/`output` (a call contract), the value is a method and is run, as now. Example: the demo's `party-search-index` becomes a fill of a `searchIndex` data slot declared by the search package, replacing the `entity-search-index/{type}` convention. Reading a data slot is pure (could also be `$func/slot-values`). It differs from `defaults`: the kind owns `defaults` and merges them into instances, while anyone contributes slot values (P11), with no merge. Ordering matters only for method fills.
- ~~Q13~~ (superseded by P8/P10: no flag, no `service` kind; singletons are a kind plus one instance that holds their configuration).: no flag, and nothing to resolve. A kind delegates by defining an operation that runs what the instance defines in its data. `service` defines exactly one, `execute({ method, input })`. The same pattern covers the mixed case: `entity-type` can define `execute` (today's entity service already has one, for extensions), and `user` then declares `set-password` in its own data, so the `user-account` subkind isn't needed (applied in [examples/f18/04-users.eson](examples/f18/04-users.eson); later simplified: `entity-type extends service`, so `execute` and the registration of instance method contracts are inherited; `service`'s `operations` field is optional). Open detail: instance methods (reached through `execute`) and kind operations are separate namespaces; a `load` check could reject instance methods that reuse a kind operation's name, to avoid confusion.

## Revisions

- **F8 (applied).** Binding through `next` was first sketched as an extra option (`{ next, context }`); replaced by `next` carrying the current `_ctx`, so `withContext` is the only binding mechanism.

- **Q15 (absolute position).** The authorization guard (07) first used `before: ["contract-updates-only-in-draft"]`, which made it name a guard it has no relation to. Added `position: "first" | "last"` as bands in the same order graph; `after`/`before` remain for real dependencies on a named fill (03).

- **F18/F19 (P8, P10).** Tried in turn: an `instanceOperations` flag; instance-defined operations through `service.execute`; a single `execute` per kind with operations as `defaults` (F19). Returned to F18: operations are a primitive property of the kind, invoked through an instance, with no `service` kind. Singletons are a kind plus one instance holding their configuration; extra operations for one entity type need a subkind (`user-account`).
- **`service` (P10).** Considered removing the `service` kind as redundant with kind-defined operations. Without it, singletons (`password`, `schema-registry`, `entity-database`) would need an extra instance to invoke on. Kept: being a service is a property (an element with operations), and the `service` kind is the kind whose instances define their own operations.
- **F9.** First stated as "a pipeline has one reader, the executor". Revised after discussion: readers that look *inside* a pipeline (durability, visualization, analysis, step extension) justify data. Black-box composition doesn't.
- **F8.** First framed as a purity violation. Revised: `_ctx` mutation is a legitimate effect (P4); the actual issue is that it creates an unscoped data-flow channel.
- **F10.** Dropped at the user's decision: no string-embedded expression syntax and no new compiler. Don't propose it again.
- **F16.** The `=` text and code mode were removed along with F10. The mode is now determined by position, using only LambdaJSON trees. Later **dropped entirely**: `/eval` is as noisy as `/data`, and the codebase has no data composition need beyond `/ref` and `/merge`. Superseded by F17.
- **F15.** "Evaluation with abstraction" removed from the core layers. Abstraction lives in kinds (F17).
- **F11.** Earlier claim that `$low` "can see `_ctx`" was wrong: `$low` and `$func` receive only their argument. Only the `low` node receives `_ctx`, and expressions have it in scope.
