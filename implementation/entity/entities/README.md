# entities

Keyed, revisioned business records, extensible by traits.

## entity-type

Each entity type is an instance of `entity-type`, or of a class: a kind that extends it, with its own fixed traits and fills (`traits`, `guards`, …). A feature is a trait, never a kind: an entity type declares the traits it has.

```json
{ "id": "order", "kind": "entity-type", "data": { "traits": { "body": { "configuration": { "schema": { "!amount": "number" } } }, "state": { "configuration": { … } } } } }
```

| Operation | Input | Output |
|---|---|---|
| `read` | `businessKey`, `revision?` (a past revision is rebuilt from history), `at?` | record, its [versioned body](#versioned-body) resolved to the version valid at `at`, the last without it; the fills of `guards` that are on `read` run on the loaded record (private `load`, which every write passes through too) as a change `{ operation: "read", before: record }` |
| `create` | `businessKey?`, `traits` (input per trait, `body` among them) | record |
| `run` | `businessKey`, `revision?`, `trait`, `operation`, `input?` | the [public operation of a trait](#public-and-private-operations) (`update` of `body`, `transition` of `state`, …); the record for an operation that writes one trait |
| `delete` | `businessKey`, `revision` | the deleted record |
| `applyChange` (private) | `change`, `revision?` | record; the write path of every write operation: the guards on the operation of the change, then the [derivation](#derived-traits) of the traits (not on `delete`), then in one transaction the store write the change implies (`create` writes `after` as derived; `trait` sets the key of each of its `commands` and of the derived commands to the command's `value` on `before`, in one revision; `delete` removes `before`) and the reactions |
| `derive` | `businessKey`, `revision?` | record; applies the [derivation](#derived-traits) to the stored record and writes the commands it gives as one `trait` change; the record as it is, without a new revision, when nothing is stale (a backfill after a rule changed) |
| `applyTraitOperations` (private) | `businessKey`, `revision?`, `entityOperation`, `operations` (`[{ key, operation, input }]`) | record; runs the trait operation of each item against the record as it is and writes their commands as one `trait` change (`invalid` for a key given twice, a key without a trait, or a trait without the operation). The nodes `traitOperation` and `traitOperations` call it |
| `initialTraitValues` | `traits` (input per trait) | the initial value of every trait, as `create` writes it |

The schema `entity-operation` is the public operation names of every kind that extends `entity-type`, registered at load. It types an argument that names an entity operation (`entityOperation` of `$func/state-forbids-operation`), so `validate()` reports a literal no entity type has, such as a misspelled `applyAmendment`.

Writes are optimistic, so no lock is held while a caller thinks and two users can't silently overwrite each other. Every write that changes a record names the `revision` it applies to. The `traitOperation` and `traitOperations` nodes and `delete` read the record (`before`) outside the transaction; the given `revision` must be `before.revision`, guards decide on `before`, and the store writes only if the record is still at that revision. Otherwise the write fails with `conflict`, so it never applies to a version the caller or the guards didn't see.

Record: `{ id, entityType, businessKey, revision, data, timestampUtc }`, where `data` maps each trait to its value; `body`, the business data, is the value of the trait `body`, checked against `<id>/body/schema`. Errors: `invalid` (a trait value, missing business key, undeclared trait), `not-found`, `conflict` (duplicate key, revision mismatch).

## Traits

An entity is a set of traits, and `data` maps each trait to its value. `body`, the business data, is the trait `body` (the kind `plain-body-trait`, configured by `{ schema }`): one key of `data`, owned by its writer, written through its command `put`, revisioned with the record and seen by guards, reactions and events in the same way as `state` or any trait to come. `entity-type` fixes no trait: an entity type declares the traits it has, and an entity without business data has no `body`. Keeping one key per trait means traits never collide with business fields and add no columns, so a feature (states, versions, ownership) is added to an entity type by configuration, not by a schema change.

- A trait is an element of a kind that extends `entity-trait`, with the schema of its `configuration`. What an entity type (or its class) names and configures is a trait; what something else contributes to it is a [slot](#slots) fill. A trait may store a value under its key (a kind that extends `valued-entity-trait` implements `initialize`) or nothing.
- A use is `{ trait?, configuration }` under a key of the `traits` property of an entity type's data. The `key` is where the value lives in `data`: the id of the trait (data of the trait element, `key`, if it declares another), so `trait` may be left out (`body`, `state`). Another trait may take over a key by declaring it, as `versioned-body` declares `body`: a contribution that names it replaces the default of the key, and two traits that don't declare the key stay a conflict. The configuration is checked against the schema the trait declares.
- A key's effective use is the deep union of its contributions, as `fixed` unites values: the same path with a different value is a conflict, nothing replaces anything. The contributions are the `fixed.traits` of the kind chain (the specification of a class, with its defaults), the `traits` of the entity type's data (what the entity type configures, and, when it has no class, its own traits), and fills of the `traits` slot, `{ trait?, key?, configuration }` with a required `configuration`, which inject a trait or specialise a use by adding paths. A key introduced only by a fill is closed to the entity type's data: if the trait matters to the business, the kind declares it.
- `validate()` reports a conflict between contributions, a configuration that doesn't match the trait's schema, an element that isn't a trait, a key used by two traits or a trait injected twice on the same target (fills that name only a key specialise the use and may repeat, their contributions are united), a trait used under a key other than its own, a key that isn't lowercase letters and digits in segments joined by `-` (a key is used in paths, so a dot would break them), a closed key in the data, and a schema with one field both optional and required.
- A package that reads a trait of a record asks for it by its kind, never by the path `data.<key>`: `$func/entity-trait-key` and `$func/entity-trait-value` (`{ record, kind }`) find the use whose trait is an instance of the kind, and the owner of a trait offers its own reader (`$func/record-body`, `$func/record-state` of [entity-states](../entity-states/README.md), `$func/record-ownership` of [entity-ownership](../entity-ownership/README.md)). A trait can then sit under another key. The core itself asks only for generic attributes of a trait, such as `identity`.
- A trait that embeds traits is not built. If a trait with an invariant of its own comes (one command that adds a version and closes a ledger entry, say), the decisions are: a level operates only on the commands its direct traits expose and what is embedded is hidden; the value of the embedding trait holds the values of the embedded ones and its command is whole; a guard sees the change of the value of its immediate container; the traits of a level are declared and fixed, so a part that comes and goes is a value, not a trait. Building it was tried and reverted: the configuration of the embedded traits has to come from the entity type, a command has to name the child it concerns, and the stored value differs in shape from the viewed one, a level of complexity that the kind which fixes two traits avoids.
- On `create`, each trait's `initialize({ entityType, key, configuration, input })` returns its initial value; `input` is `traits.<id>` of the create input.
- A value changes only through an **operation of the trait**, which is private to the entity unless the trait [makes it public](#public-and-private-operations). A trait declares operations (`update`, `amend` and `remove` of `body`, `transition` of `state`), each of which takes `{ entityType, key, configuration, value, input }` (`value` is what the key holds now, `input` what the caller gave) and returns the trait command `{ command, value }` to write. The `value` is what the store writes to the key, whole; the `command` is **metadata of the change**: it is stored nowhere, and guards, reactions and events see it in the change. The core keeps no history of commands: a feature that needs one (an audit trail, an append-only timeline) persists it from a reaction or an event consumer. The node `traitOperation: { key, operation }` runs one on the trait use under `key` (`inputMap`: `businessKey`, `revision`, `input`, and the `key` if it comes from the input) and writes the result through `applyChange`, so guards, reactions and the `revision` check apply. The node `traitOperations: [{ key, operation, input }]` runs several and writes them as **one change**: one store write, one revision, one set of guards, reactions and events, and the operation's name as the `entityOperation` that the model's `operations` by state judge; each item's `key` and `input` are mappings over the `inputMap`, and a trait appears once. A guard or reaction finds the command of one trait in a change with `$func/change-command`. The nodes are valid only in an operation of a kind extending `entity-type`: a kind declares operations of its own whose pipelines run trait operations. Every other key of `data` is carried over.
- A caller invokes the operations of the entity type, `run` among them, and only the HTTP adapters dispatch by route ([entities-http](../../adapters/entities-http/README.md), [entity-states-http](../../adapters/entity-states-http/README.md)). `$func/entity-traits` maps an entity type's keys to `{ trait, configuration }`.
- What the record shows is the trait's **view**: an optional mapping `view` in the data of the trait element, from `{ entityType, key, configuration, value, at }` to the value shown (the value itself when absent). `$func/viewed-record` applies the views of an entity type's traits to a record, `$func/viewed-change` to the `before` and `after` of a change. The records an operation returns (`read` takes `at`, which every view receives; the writes none) and the records that guards, reactions and the search index see are viewed, in the schema `viewed-entity-record`; the stored record (`entity-record`, what `entity-database` returns and a trait operation gets as `value`) is not. A view is pure and sees only its own value.

### Public and private operations

An operation of a trait is private unless it declares `public: true`; only a public one is reachable from outside, through the operation `run({ businessKey, revision?, trait, operation, input? })` of the entity type, with `trait` the key of the use: `private-operation` for anything else. A public operation is the entity's operation of its name, so the state model's `operations`, the guards (`entityOperation`) and authorization name it so (`update`, `transition`, `propose`). There are two forms, told apart by the `output` of the operation:

- **A command** (`output: "@trait-command"`, as `update` of `body` and `transition` of `state`): `run` applies it as the one trait operation of the change, with the `revision` it requires (`invalid` without, `conflict` when the record moved on).
- **A plan** (`output: "@trait-plan"`, `{ operations?, output?, commit? }`): a process of the trait. `run` starts a transaction, reads the record, runs the guards of the traits on a `trait` change named like the operation (so the state model decides, as for any operation), then the operation of the trait with the schema `trait-process-input` (`{ entityType, key, configuration, businessKey, input, record }`, `record` the viewed record), which may read and create other entities, and writes the `operations` it returns as one change at the revision it read (`revision`, when given, must be it); the result is its `output`, else the written record. `commit: false` writes nothing and returns `{ commands, entity }`: the commands the operations would write and the entity (its view) after them (a preview). A failure rolls everything back, what the process created included. [entity-amendments](../entity-amendments/README.md) is built so.

`validate()` reports two traits of an entity type that offer a public operation of the same name. The schema `entity-operation` is the names of the public operations of every kind that extends `entity-type` and of every trait, registered at load. It types an argument that names an entity operation (`entityOperation` of `$func/state-forbids-operation`), so `validate()` reports a literal no entity type has, such as a misspelled `apply`.

### Business key

The trait `business-key` (the kind `business-key-trait`) is an ordinary valued trait with `identity: true`: the core knows only that attribute, takes the record's `businessKey` from the value of the trait that has it, and `validate()` reports an entity type with none or with several. The value lives in `data['business-key']`. Its `initialize` returns the `businessKey` the caller gave, else the result of `rule`, else raises `invalid`. `rule` is an optional method in the configuration, run with the create input as `#.input` (`traits.body` is the business data); it may have effects, such as a sequence. Every trait's `initialize` also receives the whole create input as `create`. Every entity type has the trait (`entity-type` fixes it), so an entity type adds only a `rule`. The configuration of a trait is united, never replaced: a class and an entity type can't give different rules.

### Hooks of a trait

The entity type drives its traits, and a trait tells it what to do at three points of a write with a **hook**: a method in the data of the trait element, beside `configuration` and `view` (`guard`, `react` and `derive`, below). A hook is not an operation of the trait's kind: no caller invokes it, and the entity type runs it with `execute` for every trait of the type that has one (`$func/instance-methods` lists the methods of a property across the instances of a kind, and the effect inference counts them, so the bounds of a guard and of a transaction hold). It sees the entity type as `#.self` and takes `{ entityType, key, configuration, … }` as `#.input`.

### Guard of a trait

The hook `guard` takes `{ entityType, key, configuration, change }` (`change` is the viewed change, as the slots get it). It runs before the guards of the slot, at `load` for a read and in `applyChange` for a write; it throws to refuse and may only read and trace (`validate()` reports a guard with another effect). The hook decides from `change.operation` which changes concern it. The trait's own behaviour thus travels with the trait: [entity-states](../entity-states/README.md#operations-by-state) refuses an operation outside its states with the `guard` of the `state` trait, and no fill is needed. A fill stays for what something else contributes to an entity type. The folds belong to the kind `trait-container`, which `entity-type` extends and which holds the slot `traits`, `initialTraitValues`, `deriveData`, and `guardTraits`.

### Reaction of a trait

The hook `react` takes `{ entityType, key, configuration, change }` (`change` is the viewed change with `after` the written record, as the slot `reactions` gets it). It runs in the transaction of the write, after it and before the fills of `reactions`; it may write (through other entities' operations), and a failure rolls the write back. A trait that has `react` is a reactive trait: its configuration says what its entity type does when it changes, so the entity type needs no fill. [entity-amendments](../entity-amendments/README.md) has one (`amending`). A fill stays for what something else contributes to an entity type.

### Derived traits

The hook `derive` takes `{ entityType, key, configuration, record }` (`record` is `{ entityType, businessKey, data }` as the write leaves it) and returns a trait command for its own key, or `null` when its value stays; the command may carry `operations: [{ key, operation, input }]`, trait operations of other traits that run on the record with the command applied and whose commands join the change (the validations ask the `state` trait for a transition so). `applyChange` folds the derives over the traits, in the order of `$func/entity-traits`: each sees the record with the commands so far applied (a command's value replaces the key whole, it is not merged into it) (the caller's, the `initialize` values on `create`, and the earlier derives'), so the output of one is visible to the next. The commands of the derives join the change's, in the same revision. A trait that offers another way to change its value sees the command already given for its key and decides what to do with it: nothing in the framework reconciles the two (the rule "a write changes a trait once" binds the caller's operations only). The kind `entity-type` exposes `derive`, which runs the fold over a stored record. [entity-ownership](../entity-ownership/README.md) is such a trait.

**Where the rule of a derived fact is written** depends on where the fact lives and on how many parties give rules:

| The fact | One rule, given by the entity type | Rules several parties contribute, united | Example |
|---|---|---|---|
| lives in the record, under the key of a trait | the `configuration` of the trait | a slot declared by the package of the trait, whose `derive` unites the results | [ownership](../entity-ownership/README.md) · [validations](../entity-validations/README.md) |
| lives outside the record (a table, an index) | a slot of one, filled by the entity type | a slot of many, maintained by a `reactions` fill | [search](../entity-search/README.md) · [relations](../entity-relations/README.md) |

A rule computes from the record as the write leaves it. A class fixes what must not vary (the dimensions of ownership) in `fixed`, and the entity type gives the rest.

### Versioned body

The trait `versioned-body` (the kind `versioned-body-trait`, which takes over the key `body`: an entity type names it, `"body": { "trait": "versioned-body", … }`) stores the body as a timeline; its configuration adds the required `versioned: { validFrom }` (`validFrom` is a JSON pointer to the field of the body that says from when it is valid, e.g. `/startDate`). The timeline is a list of versions `{ validFrom, ref?, body }` in the order they were added, `validFrom` being that date and `ref` the business key of the amendment that made it (none for the first version), the last body in full and earlier ones as backward patches. Every amendment adds a version of its own, also at the date of the last one, which it then shadows (the version valid at a date is the last one in the list that is valid from it or before), so `remove` of it brings the earlier one back. A body without the date is dated `undated`, until a date replaces it.

- `create` and `update` take the plain body: `update` corrects what is there and replaces a timeline of one version (its date may change); once amended, `update` is `conflict`. The operations `amend({ validFrom, ref, body })` (`ref` names who manages the version; `body` is the whole new version, which the trait checks against the schema and dates `validFrom`; the pure function `$func/patched-body` makes one from the last version and a JSON Patch) and `remove({ validFrom, ref })` of the trait add and drop the last version, `remove` only if the last version is that of `validFrom` and `ref`; an entity that is amended exposes them through operations of its own (`traitOperation`). The state model's `operations` says in which states.
- Every record an operation returns, and the records that guards and reactions see (`before`, `after`), carry the body of the last version, so a rule is written against the body whether it is versioned or not. The raw timeline is what the store holds and what a trait operation gets as `value`. Its view is the version valid at `at`, the last without one; `read` at an `at` before the first version is `not-found`.
- The schema `<id>/body/schema` describes the whole body, every version of it.

The `state` trait is [entity-states](../entity-states/README.md).

## Slots

Fill them on `entity-type` (every entity type), on a class (all its instances) or on one entity type.

| Slot | Cardinality | Value | Runs |
|---|---|---|---|
| `traits` | many | `{ trait?, key?, configuration }` | see [Traits](#traits) |
| `guards` | many | method: change → (throws to refuse); [effects](../../core/README.md#effects) `read` and `trace` only; discriminator `operation`, a fill says with `on` which operations it judges ([slots](../../core/README.md#slots)) | before the transaction |
| `reactions` | many | method: change with `after` = the written record | inside the transaction, after the write; a failure rolls back; no `irreversible` effects outside `afterCommit` (the outbox defers delivery so) |

A change is one of four variants by its `operation` (`entity-change`): `create` carries `after` (`businessKey`, `data`), `trait` the `before` record and the written `commands` (`{ key, command, value }`), `delete` and `read` the `before` record; reactions see `after` as the written record. The input of a guard fill that is `on` some operations has only their fields, so a guard `on: ["read"]` that reads `commands` is reported by `validate()`. `entityOperation` (any variant) names the operation of the entity type that causes a `trait` or `delete` change (`update`, `putSegment`, `delete`, …), so that a guard can decide on what the entity exposes and not on the trait it ends in.

### Order of a write

1. `load` reads the record and runs the guards `on` `read`: whether a record is visible is decided here, once, for `read`, `derive` and every write, before anything computes on it (a hidden record is `not-found`, never an `invalid` from a trait operation).
2. The operation computes its commands (trait operations) and calls `applyChange`.
3. `applyChange` checks the `revision`, runs the guards `on` the operation of the change (`create`, `trait` or `delete`), folds the [derivation](#derived-traits), then in one transaction writes and runs the reactions.

A guard without `on` judges every operation, so it runs in step 1 and again in step 3.

## Storage

`entity-database` (kind `entity-store`) runs the store operations `create`, `read` (at an optional `revision`), `update({ before, values })` (replaces the keys of `data` that `values` maps), and `delete({ before })`, each through its [query](../../platform/database/README.md#queries) (`create-entity`, `read-entity`, `update-entity`, `delete-entity`), which owns the contract; the operations of the kind declare the same schemas (`entity-create-input`, `entity-key`, `entity-update-input`, `entity-delete-input`, output `entity-record`), so another store implements typed operations. The query `list-entities` is not a store operation: a backfill or a reindex, run as the system, calls it to enumerate the records of a type (`entityType`, `limit`, `offset`; `{ items, total }`). `update` and `delete` apply only at `before.revision` (`conflict` otherwise); the store writes in the bound `transaction`, if any. Implementation: [entities-postgresql](../../adapters/entities-postgresql/README.md).
