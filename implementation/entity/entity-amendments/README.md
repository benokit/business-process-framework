# entity-amendments

Changes to an entity with a versioned body as entities of their own: an amendment is proposed, issued, activated, and may be annulled. Activating one amends the entity from a date; annulling it takes the version away. The mechanism of versions is the trait `body` of [entities](../entities/README.md#versioned-body); this package is the process around it, and an application builds on it or writes its own.

- **`versioned-entity-type`** (kind, extends `stateful-body-entity-type`): an entity type whose body is versioned and that can be amended. It fixes the trait `amendment-ledger`, has the slot `amendmentTypes` (the fills that say which `amendment-entity-type`s may amend it, and how) and the operations `applyAmendment({ businessKey, revision, operations })` and `revertAmendment({ businessKey, revision, operations })`, which write the trait operations in `operations` (`[{ key, operation, input }]`) as one change, and `previewAmendment({ businessKey, operations })`, which returns their commands (`[{ key, command, value }]`) and writes nothing. The amendment knows no trait: what it does to the entity is a list of trait operations. The concrete type configures the body (`versioned.validFrom`) and its state model. Whether an entity can be amended is its model: `operations` lists `applyAmendment` for the states it is possible in, as for `update`.
- **fills of `amendmentTypes`**: a bare reference to an amendment type, or `{ type, open?, apply?, revert?, input? }`, where `open` is a mapping, `apply` and `revert` are lists of trait operations `{ key, operation, input }` whose `input` is a mapping, and `input` of the fill is the id of a schema. `open` maps `{ entity, input }` (the entity as its type reads it, and the `input` of `propose`) to the amendment's initial body. The `input` of an item of `apply` or `revert` maps `{ body, amendment, link }` (the body of the entity's last version, the amendment and its `amendment-link`); the items of `apply` are written as one change when the amendment is applied, those of `revert` when it is annulled, so the body and the state (or any other trait) move together in one revision and one event. Without `apply` it is `body.amend` with the amendment's body valid from the `effectiveFrom` of the link, and without `revert` it is `body.remove` of that date, which is how a bare reference amends by copying the last version; `$func/patched-body` makes a body from the last version and a patch. `input` of the fill checks the input of `propose` before `open` runs. `validate()` reports a mapping that reads a path its scope hasn't (`unknown-path`) and a result that isn't what it produces: `open` is checked against the body schema of the amendment type, the `input` of an item against the input of its trait operation (that of `body` with the body schema of the entity type: a field of the wrong type, a required one missing, one the schema closes out), an item whose trait or operation the entity type hasn't, a trait used twice in a list and a trait that `apply` changes and `revert` doesn't. What the data flow can't tell, such as a value read from an open schema, isn't reported.
- **`amendment-link`** (trait, `amendment-link-value`): `{ amendedType, amendedKey, amendedRevision, effectiveFrom }`, the facts the process owns, fixed at `propose`: what the amendment amends, the revision of the entity it was proposed at (after the ledger write) and from when it is valid.
- **`amendment-ledger`** (trait, no configuration): `{ last, open }`, the number of the last amendment and the key of the open one (`null` if none). Its `guard` ([hook of a trait](../entities/README.md#hooks-of-a-trait)) accepts only the commands `open` and `close` with a value of that shape.
- **`amendment-entity-type`** (kind): the dimension `versionStatus` of its `state`: `pending` (the change is being made or reviewed, not in the entity's versions), `applied` (its version is in them) and `discarded` (it is not, or no longer is), moving `pending` → `applied` → `discarded` or `pending` → `discarded`, a graph the kind declares in its model ([restricting the moves](../entity-states/README.md#restricting-the-moves-of-a-dimension)), so that `validate()` reports a process that moves it any other way or starts it elsewhere than `pending`. The **process** is the application's own, in other dimensions (an approval with `status`, say) and in transitions of its own names, each of which moves `versionStatus` where it should; a relation `amends`; the body schema is the concrete type's own (a copy of the entity's, a reason and typed changes, …). The operation `preview({ businessKey })` returns the version `apply` would add, `{ validFrom, body }`, and writes nothing; who may call it is the authorization of operations, per state. A guard refuses to `create` one other than through `propose`.
- **`entity-amendments`** (instance of `entity-amendment-process`):

| Operation | Input | Effect |
|---|---|---|
| `propose` | `entityType`, `businessKey`, `amendmentType`, `effectiveFrom`, `input?` | in one transaction: the entity must allow `applyAmendment` in its state (`conflict`), have a fill for the type (`invalid`; so is an `input` that doesn't match the fill's schema) and have no open amendment (`conflict`); writes `last + 1` and the new key as `open` in the ledger at the entity's revision, and creates the amendment `<businessKey>-<number>` (`%03d`) with the body `open` gives and the `amendment-link`. Concurrent proposals can't both win and the numbers have no gaps |
| `preview` | `entityType`, `amendment` | the commands that `apply` would write, `[{ key, command, value }]`: the `apply` items of the fill, mapped over the entity's last version, the amendment and its link, run by `previewAmendment` |
| `apply` | `entityType`, `amendment` | when `versionStatus` goes `pending` → `applied`: `conflict` if the entity is no longer at the revision of the link, else `applyAmendment` of the entity with the `apply` items of the fill (`conflict` if the body's date is before the last version, or a state can't move), then `close` |
| `revert` | `entityType`, `amendment` | when it goes `applied` → `discarded`: `revertAmendment` of the entity with the `revert` items of the fill; only the latest version can go, so annulments run in the reverse order of activations (`conflict` otherwise) |
| `close` | `entityType`, `amendment` | when it goes `pending` → `discarded`, and after `apply`: the ledger's `open` is `null` again; `conflict` if the amendment is not the open one |

`apply`, `revert` and `close` are the reactions of `amendment-entity-type` to those moves, in the transaction of the transition: a failure rolls the transition back. The context `amending` (managed by the process) is what lets `propose` create an amendment.

What the package leaves to the application: an HTTP route for `propose`, who may do what ([authorization](../../services/authorization/README.md), per state with [state-permissions](../../services/state-permissions/README.md)), the amendment types and the shape of their data, and how the `input` of `propose` becomes an amendment and an amendment a version (the fill). The demo's fills turn a flat `changes` object into a patch ([amendment endpoint](../../../demo/contracts/amendment-endpoint.eson)).

```json
{ "id": "policy", "kind": "versioned-entity-type", "data": { "traits": { "body": { "configuration": { "schema": { "!startDate": "@date", "!premium": "number" }, "versioned": { "validFrom": "/startDate" } } }, "state": { "configuration": { "…": "a model with operations: { applyAmendment: { status: { active: true } } }" } } } } }
{ "id": "premium-raise", "kind": "amendment-entity-type", "data": { "traits": { "body": { "configuration": { "schema": { "!reason": "string", "!premium": "number" } } }, "state": { "configuration": { "…": "a process: states of its own, and transitions that move versionStatus, such as approve: { versionStatus: { pending: applied } }" } } } } }
{ "id": "policy-premium-raise", "kind": "slot-fill", "data": { "target": "policy", "slot": "amendmentTypes", "value": { "type": "premium-raise", "apply": [{ "key": "body", "operation": "amend", "input": { "validFrom": "#.link.effectiveFrom", "body": { "$func/patched-body": { "body": "#.body", "patch": [{ "op": "replace", "path": "/premium", "value": "#.amendment.data.body.premium" }] } } } }] } } }
{ "id": "policy-cancellation", "kind": "slot-fill", "data": { "target": "policy", "slot": "amendmentTypes", "value": { "type": "cancellation", "apply": [{ "key": "body", "operation": "amend", "input": { "validFrom": "#.link.effectiveFrom", "body": { "$func/patched-body": { "body": "#.body", "patch": [{ "op": "add", "path": "/endDate", "value": "#.link.effectiveFrom" }] } } } }, { "key": "state", "operation": "transition", "input": { "transition": "cancel" } }], "revert": [{ "key": "body", "operation": "remove", "input": { "validFrom": "#.link.effectiveFrom" } }, { "key": "state", "operation": "transition", "input": { "transition": "reactivate" } }] } } }
```
