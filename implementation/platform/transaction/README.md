# transaction

Transactions as scoped context, on the sessions of the bound [`database`](../../platform/database/README.md). The transaction is bound for a subtree rather than passed as an argument, so every store call inside it joins it without its signature mentioning it, and `afterCommit` can defer what must happen only once the work is durable.

- Kind `transaction-manager`, instance `transaction` (`isolation`: `read committed`, `repeatable read` or `serializable`): `begin()` → `{ sessionId }`, `commit({ sessionId })`, `rollback({ sessionId })`, through the database's; `savepoint({ sessionId })` → `{ sessionId, name }`, `releaseSavepoint` and `rollbackToSavepoint` (both take that) on the same session, and the last drops the `afterCommit` work registered since the savepoint.
- Keyword `afterCommit` (instance `after-commit`, [`effects.defers`](../../core/README.md#effects)): its pipeline runs after the bound transaction commits, or at once when no transaction is bound; a rollback drops it. Inside a joined transaction it runs after the outermost commit. It runs in registration order, with the node's input, the `self` of the code it is written in and the caller's context without `transaction`; pass outputs it needs through `inputMap`. The committed work has succeeded whatever the pipeline does: a failure is ignored, so the pipeline handles its own.
- Keyword `inTransaction` (instance `in-transaction`, a [`transaction-execution-node-wrapper`](../../platform/database/README.md)): runs its pipeline in the caller's context with `transaction` bound, commits on success, rolls back and rethrows on failure. Inside an enclosing transaction it joins it; sequential nodes each start their own. Its pipeline may only have `read`, `write` and `trace` [effects](../../core/README.md#effects): `validate()` reports an `irreversible` effect it reaches, unless it runs under `afterCommit`.
- Keyword `inSavepoint` (instance `in-savepoint`, the same kind of wrapper): runs its pipeline as an **atomic scope** of the bound transaction. It takes a savepoint, releases it on success, and on failure rolls back to it (the writes, the messages put in the outbox and the `afterCommit` work of the scope are gone, and the transaction is usable again, which an SQL error otherwise prevents) and rethrows, so a `try` around it can take another path with nothing of the scope left behind. The enclosing transaction continues and commits what came before and after. Outside a transaction it is `invalid`, since there is nothing to roll back to: wrap the work in `inTransaction`. It has the same effect bounds as `inTransaction`.

```json
{ "inTransaction": [ { "invoke": "contract", "operation": "update" }, { "publish": "contract-events" } ] }
```
