# demo

An insurance application built on the [framework](../implementation/README.md): parties (searchable, with a `parties-by-type-search-query` search query at `POST /parties/search-by-type`) and construction contracts (an entity class with a numbered business key, a policyholder relation, a draft-only update guard and a `contract-activated` event). What varies in time is the `versionable` timeline of the contract class (`premium`, `sumInsured`, `endDate`), whose first version is the start of the contract; the body keeps what never varies (policyholder, project, currency). How an entity with a timeline is amended is not specific to contracts and lives in [versioning](versioning/): `versioned-entity-type` (an entity type with its timeline under the fixed key `timeline`, whose segment schema a concrete kind sets by filling the same key, an `amendment-ledger` trait that takes no configuration, guards that accept the ledger only through `open` and `close` with the value `{ last, open }` and the timeline only through `put` and `remove`, the slot `amendmentTypes` and the abstract operation `isAmendable`, which `insurance-contract-type` implements as amendable when active), `amendment-entity-type` (lifecycle draft, issued, active, cancelled, annulled, a relation `amends`, guards and the reactions that apply, revert and close) and the process `entity-amendments`. Premium adjustments and extensions ([amendment-types.eson](contracts/amendment-types.eson)) are amendment types that hold the `changes` to the terms, an effective date and a reason; a contract type lists the types it allows (marine only the first). An amendment is created only by `POST /entities/:entityType/:businessKey/amendments`, which needs an amendable entity and an allowed type and binds the context `amending`, without which a guard refuses `create`. The entity keeps the `amendment-ledger` (`{ last, open }`): proposing writes `last + 1` and the new key as `open` in the same transaction as the amendment, at the entity's revision, so only one amendment is open (draft or issued) at a time, concurrent proposals can't both win, and the numbers have no gaps; activating or cancelling an amendment closes it. The key is the entity's key and that number (`<contract key>-001`). Activating an amendment merges its changes into the terms current then and adds them from the effective date, annulling an active one removes them, and only the latest can be annulled, so annulments run in the reverse order of activations; cancelling one that never took effect (draft or issued) changes nothing. The underwriter proposes, issues, cancels and annuls amendments, an administrator activates them. Marine contracts ([marine.eson](contracts/marine.eson)) are another contract type whose lifecycle is composed from the construction one with `/ref` of a path and `/merge`: they add the state `suspended`, the transition `suspend` and `cancel` from it. [Roles](security/roles.eson): an `underwriter-role` (its own `underwriter-actor`: contracts, their transitions except `activate`, and parties; plus the framework's `entity-reader-actor`), a `viewer-role` and an `administrator-role` ([authorization](../implementation/framework/authorization/README.md)). The migration [`administrator-user`](security/administrator.eson) creates the user `administrator` with the administrator role; the demo's [app config](security/app-config.eson) maps the login `admin` to it (the `actAs` setting of `authenticate`), so a token of the mock identity provider for `admin` administers users. A real deployment leaves that file out and maps its own login (`BPF__security__actAs__administrator=<subject>`).

```sh
cd implementation/server && npm run start-demo   # bpf migrate ../../demo, then start
```
